## 二、原稿与后端事实不符的 8 处（以后端为准）

### 2.1 交易与拍卖不是「要新建」，是「已建好、关着」

后端 `src/market/market.controller.ts` 已提供 8 个玩家端接口，全部 `@Idempotent()`：

```37:137:src/market/market.controller.ts

  @Post('gift')                   gift(...)          // 3b 定向赠送

  @Post('listings/:id/bid')       bid(...)           // 3d 竞价出价
```

配套的也都在：`market_listing` / `market_bid` 表已建（含 `uq_bid_active_bidder`、
`uq_listing_instance_active` 等并发约束索引）、`ESCROW` 托管账户已建（实测 `account` 表
第 2 行，`system_code='ESCROW'`）、`market-settle` cron 每 5 分钟跑一次自动结算与流拍退回。

**当前之所以「看不见」，是因为实库配置全关：**

```

market.features = { "gift": false, "auction": false, "listing": false, "recycle": false }
```

> **结论**：P5 的开启动作是在后台「配置中心」把这两项改成 `true`，**不写一行代码**。
> 原稿的「P5 工作量：大」应改为「后端零、前端中」。

#### `⟳ 复核补充` 总闸不是「一刀切」：前端必须按这张表处理

原文只说了「配置全关」，没说**关的时候每个接口各自是什么行为**。
前端如果按「关了就全都不能用」去写，会在两处出错。实测 gating 如下
（`TradeRiskService.assertEnabled()` 的调用点，逐个数出来的）：

| 接口 | 受总闸约束 | 关闭时的实际行为 |
| --- | --- | --- |
| `GET /market/listings` | ❌ **不受约束** | 正常 200，返回 `{ list: [], total: 0 }` |
| `GET /market/my-listings` | ❌ **不受约束** | 正常 200，能看到历史挂单 |
| `POST /market/recycle` | ✅ `recycle` | **403** |
| `POST /market/gift` | ✅ `gift` | **403** |
| `POST /market/listings` | ✅ `listing` 或 `auction`（按 `mode`） | **403** |
| `POST /market/listings/:id/buy` | ✅ `listing` | **403** |
| `POST /market/listings/:id/bid` | ✅ `auction` | **403** |
| `POST /market/listings/:id/cancel` | ❌ **刻意不受约束** | 正常执行，能撤单 |

两个要点，都是前端会写错的地方：

1. **拒绝是 403 `ForbiddenException`，不是 400**。message 分两种：
   总闸关是 `交易功能暂未开放`，总闸开但分档关是 `该交易方式暂未开放`。
   前端应把这两条渲染成「暂未开放」的空状态，**不要弹错误 toast**——
   灰度期间这是预期行为而非故障。
2. **撤单通道永远开着，前端不能因为总闸关了就隐藏撤单按钮。**
   `market.service.ts:387` 有一段显式注释说明这不是漏写：

```8:16:src/market/market.config.ts
 * `market.enabled` 是总闸（风控清单 R10）：关掉它之后**建仓类**写操作立刻拒绝
 * （回收 / 赠送 / 挂单 / 出价 / 一价成交），已挂的单不会消失、已冻结的资产不会丢。
 *
 * ⚠ **平仓类操作刻意不受总闸约束**，别把它们"补齐"成也要校验：
 * 玩家撤单（`MarketService.cancel`）、后台强制撤单、到期退回、竞价结算走的都是
 * `TradeSettlementService.unwind`，总闸关闭时依然可用。理由是关市场的典型场景就是
 * 「出事了先止血」，此时标的还在 ESCROW、买家的钱还在冻结里 —— 若连退出通道一起关掉，
 * 玩家资产就被永久锁死，而这比让市场多开几分钟严重得多。
 * 换句话说总闸的语义是"不许再进场"，不是"冻住所有人"。
```

> 这条语义对**新玩法也是范式**：任何带冻结/托管的新功能（繁殖扣体力不算，
> 但 P12 活动若有押金类设计就算），开关只该拦「进场」，不该拦「退出」。

### 2.2 数据库 CHECK 约束禁止「扭蛋产出可交易」——这否决了原稿的经济闭环

`asset_def` 上有三条硬约束，写死在库层：

```42:52:src/entities/asset-def.entity.ts
@Check('ck_asset_kind', `"kind" IN ('currency','stackable','unique')`)
@Check('ck_asset_no_trade_redeem', `NOT ("tradable" AND "redeemable")`)
@Check('ck_asset_no_trade_gacha',  `NOT ("tradable" AND "gacha_output")`)
@Check('ck_asset_expire_days', `"expire_days" IS NULL OR "expire_days" > 0`)
@Check('ck_asset_mint_limit', `"mint_limit" IS NULL OR "minted_count" <= "mint_limit"`)
@Check('ck_asset_cooldown', `"trade_cooldown_hours" >= 0`)
```

原稿 P8 设计「稀有 = 扭蛋产出」「稀有宠物能卖高价游戏币」，
而 `ck_asset_no_trade_gacha` 明确规定 **`tradable` 与 `gacha_output` 不能同真**。
实库里 `skin_shadow`、`bg_beach`、`cons_snack/bubble/energy/cake` 全是 `gacha_output=true`，
因此全部 `tradable=false`——**它们永远上不了拍卖行**。

这不是疏漏，是「开箱即可变现」合规红线的结构性防线（可交易 + 随机产出 = 开箱变现模式）。

> **结论（以后端为准）**：**玩家间流转**的稀缺来源不能是扭蛋产出物。
> 可在拍卖行流通的稀缺来源只有两类：
> 1. **限量铸造**——`mint_limit` + `serial` 编号（实库 `skin_aurora` 已是 `mint_limit=100`、`tradable=true` 的范例）；
> 2. **繁殖 / 融合产出**——新造的资产定义为 `gacha_output=false, tradable=true`。
>
> 前端不要再把「扭蛋稀有档」当作可交易稀有物的来源。
> 原稿 P2 的 `pp_bug`（扭蛋稀有档获取）必须建为 `tradable=false`。

**但扭蛋产出并非完全没有变现出口。** 系统回收（3a）刻意放宽了可交易校验：

```722:726:src/market/market.service.ts
   * 解析交易标的：校验归属、状态、冷却与可交易性。
   *
   * `requireTradable` 对回收是 false：不可交易的扭蛋限定款仍然可以卖给系统 ——
   * 回收没有对手方，不构成玩家间流转，因此不触及「开箱变现」那条红线。
   */
```

所以完整的价值兑现图景是**两条路而不是一条**：

| 稀有来源 | 玩家间交易 | 卖给系统（`/market/recycle`） |
| --- | --- | --- |
| 扭蛋产出（`gacha_output=true`） | ❌ CHECK 禁止 | ✅ 按 `recycleRateBps`（当前 30%）折价 |
| 限量铸造 / 繁殖 / 融合 | ✅ 拍卖行 | ✅ 同样可回收 |

> 这条设计很讲究：回收率被刻意压到 30%（配置上限 90%），
> 所以「买入再回收」必然亏——回收是 sink 不是套利通道。
> 对 P8 的意义是：**扭蛋稀有款仍有游戏币出口，只是折价的单向出口**，
> 攀比价值要靠图鉴与展示（P9）兑现，而不是靠挂高价。
> 原稿「稀有宠物能卖高价游戏币」这句，只对繁殖/融合产出成立。

### 2.3 「不设手续费、不限次数」与后端**已实现并生效**的风控冲突

原稿第六节写「不做经济调控，不收手续费、不限次数」。实库配置是：

```
market.feeBps         = 500            # 成交手续费 5%，进 FEE 账户即退出流通
market.listingHours   = 72             # 挂单有效期
market.recycleRateBps = 3000           # 系统回收价 = 商店价 30%
market.priceBand      = { "enabled": true, "minBps": 5000, "maxBps": 100000 }
market.risk           = { "minAccountAgeDays": 7, "maxTradesPerDay": 20,
                          "maxValuePerDay": 100000, "abnormalPriceRatio": 8 }
```

这些不是「经济平衡调参」，是**风控与反套利**（代号 R1/R3/R5/R6/R9/R10），
并且 `trade_risk_daily` 表、`TradeRiskService`、后台「净流出风控」页都已围绕它们建成。
`market.priceBand` 的注释说明了它真正的目的：**堵住「1 币挂高价物」的站外交易通道**。

> **结论（以后端为准）**：手续费与风控**保留**。
> 原稿「不设手续费与交易次数限制」一节作废。
> 若确实要放宽，走后台配置中心调数值（`feeBps` 可设 0、`maxTradesPerDay` 可调大），
> **但 `priceBand` 与 `minAccountAgeDays` 不建议关**——它们防的是站外套现，不是通胀。

```46:56:src/pet/pet.service.ts
  /** 因每日上限被截断 */
  capped: boolean;
  levelUp: boolean;
  cooldownRemainMs: number;
  /** 发币后的最新游戏币余额（未发币则为发币前余额） */
  gameCoin: number;
}
```

所以前端现在从 `/pet/feed` 读 `res.gameCoin` 是**对的**，不要盲目全局替换。

> **结论（两条，分开执行）**：
>
> 1. **所有新接口一律用 `wallet: WalletView`**，不新增裸 `gameCoin` 字段。
>    本文档后续所有契约都按这条写。
> 2. **建议把 `/pet/*` 的 `gameCoin` 也统一成 `wallet`**，作为一次显式的破坏性变更。
>    理由不是「整齐」，而是**市场一开，裸 `gameCoin` 就会骗人**——
>    它是 `balances[GAME_COIN].available`，不含冻结额。玩家挂单出价后
>    看到余额变少却找不到钱去哪了，而 `WalletView` 的 `gameCoinFrozen`
>    正是为此存在的。这条变更应与 §10.1 开启市场**同批上线**，
>    在那之前它只是风格问题，在那之后它是正确性问题。

### 2.5 错误格式：`{ code, message }`，不是 HTTP 语义碎片

```41:41:src/common/filters/all-exceptions.filter.ts
res.status(status).json({ code: status, message });
```

`code` 就是 HTTP 状态码，`message` 是中文文案（可能是字符串或字符串数组——
class-validator 校验失败时是数组）。

> **结论**：原稿里「错误：400 `宠物未成年`」这类写法保留语义，但前端解析统一走
> `res.data.message`，并处理 `message` 可能是数组的情形。

### 2.6 分页：统一 `{ list, total }`，参数是 `page` / `pageSize`

```8:21:src/common/dto/pagination.dto.ts
page: number = 1        // @IsOptional @IsInt @Min(1)
pageSize: number = 20   // @IsOptional @IsInt @Min(1) @Max(100)
```

> **结论**：原稿 `GET /pvp/rank` 返回的 `{ list, total, myRank, myRankPoint }`
> 改为 `{ list, total, me: { rank, rankPoint } }`——平铺的 `myXxx` 不符合既有出参风格，
> 且「我的排名」是一个对象而非两个孤立字段。`pageSize` 上限 100，前端不要传更大值。

### 2.7 拍卖没有 `claim`：结算是服务端 cron，不是玩家领取

原稿设计 `POST /auction/claim`（领取拍得物品或流拍退回）。后端不需要：

```27:27:src/market/market-settle.service.ts
@Cron('*/5 * * * *', { name: 'market-settle', timeZone: 'Asia/Shanghai' })
```

到期挂单由定时任务自动结算：价高者得则转移标的 + 分账 + 扣手续费，
无人出价则原物退回卖家、解冻所有出价。全程走账本凭证，玩家无需操作。

> **结论**：`POST /auction/claim` **不实现**。
> 前端删掉「领取」按钮，改为轮询 `GET /market/my-listings` 看状态流转
> （`listed → sold / expired / cancelled`）。这比让玩家手动领取更符合「服务端权威」。

`⟳ 复核补充` — 为什么必须是 `my-listings` 而不能是 `listings`：实测 `browse()` 的 where 是
`status = 'listed' AND expires_at > now()`，**只返回在售且未过期的**。
所以「我拍中了」「我流拍了」这两个状态**在市场浏览接口里永远看不到**，
`GET /market/my-listings` 是唯一出口（它查全状态，不加时间过滤）。

`⟳ 复核补充` — 排新 cron 时要避开已占用的时间点。实库当前跑着 **5 个** cron，
凌晨 4 点前后已经很挤：

| cron | 表达式 | 位置 |
| --- | --- | --- |
| `monthly-partition` | `30 3 1 * *` | `src/ledger/partition.service.ts:62` |
| `daily-expire` | `0 4 * * *` | `src/ledger/expire.service.ts:58` |
| `daily-reconcile` | `10 4 * * *` | `src/economy/reconcile.service.ts:79` |
| `market-netflow` | `20 4 * * *` | `src/market/market-settle.service.ts:65` |
| `market-settle` | `*/5 * * * *` | `src/market/market-settle.service.ts:27` |

全部 `timeZone: 'Asia/Shanghai'`，且当前是 **PM2 单实例**，没有分布式调度——
所有 cron 在同一进程里跑。本方案要加的 `pet-condition-scan`（§6.3，`15 * * * *`）
与 `pvp.season.cron`（§9.3，默认 `0 5 * * 1`）都没冲突；
但**别再往 4:00–4:30 这个窗口塞东西**，那里已经串了三个重活（过期销毁 → 全量对账 → 净流出统计）。

### 2.8 「6 只上限」是配置项，不需要拆「出战位 + 仓库」

原稿 9.2 提出方案 B「后端把 6 只上限拆成出战位 6 + 仓库 30」，并说是接口变更。实际上：


> **结论**：方案 B 作废，方案 A（3 只一组融合）也不必因上限而妥协。

## 三、新玩法必须遵守的后端既有范式

这一节是**给后端实现者的硬约束**，也是估算工作量的依据。所有新玩法一律照此写，不另起炉灶。

### 3.1 配置：声明在域内，注册表自动汇总

新增一个可调值 = 在 `src/<域>/<域>.config.ts` 里加一条 `defineConfig`，
然后在 `src/config/game-config.registry.ts` 里 spread 进去。

`⟳ 复核修正` — 注册表当前 spread 了 **11 个域**（`PET` / `RACE` / `DAILY` / `BOOST` /
`DEX` / `EXCHANGE` / `GACHA` / `HOME` / `ITEMS` / `MARKET` / `PROMO`）。
原文说「新增一个可调值只需改动对应域的文件，不必碰这里」——这句只对**在既有域里加 key** 成立。
本方案要新建 7 个域（`breed` / `pvp` / `clinic` / `fusion` / `minigame` / `training` / `event`），
每建一个都**必须**在 `game-config.registry.ts` 加一行 `import` 加一行 spread，
漏了的表现是「配置项在代码里有、后台配置中心看不到、`snapshot()` 取值走默认值」——
不报错，静默失效，是本方案里最难查的一类 bug。

```9:24:src/config/game-config.types.ts
export interface ConfigEntry<T> {
  description: string;
  schema: Joi.Schema;     // 后台写入时按它校验，非法值直接拒绝
  default: T;             // 同时是启动种子初值与 DB 脏数据兜底
}
export function defineConfig<T>(entry: ConfigEntry<T>): ConfigEntry<T> { return entry; }
```

运行时取值链路：`GameConfigService.snapshot()` 读 `game_config` 表 → Joi 校验 →
非法则回退默认值并告警 → 30 秒内存缓存。启动时 `seed()` 在锁内补齐缺失 key，
**永不覆盖已有行**（运营改过的值不会被发版冲掉）。

> **这条的价值**：新配置项**自动出现在管理后台「配置中心」**，前端零改动。
> 见 §3.7。

### 3.2 账本：不要自己写 SQL 加减余额

一切资产变动走 `RewardService`（多资产原子）或 `EconomyService`（单池货币便捷入口）：

```48:74:src/ledger/reward.service.ts
async grant(userId, rewards: Reward[], ctx: RewardCtx): Promise<PostResult>
async charge(userId, costs: Reward[], ctx: RewardCtx): Promise<PostResult>
async exchange(userId, costs: Reward[], rewards: Reward[], ctx: RewardCtx): Promise<PostResult>
```

`Reward = { assetCode, count }`；`RewardCtx = { reason, bizKey, refType?, refId?, scope? }`。

**「扣币 + 发道具」必须用 `exchange` 一次调用**，不能连调 `charge` 再 `grant`——那不是原子的。
繁殖（扣 500 币产蛋）、治疗（扣币或扣药）、融合（消耗宠物）全都属于这一类。

`reason` 是白名单（`LEDGER_REASONS` 常量数组，落 varchar 不落 pg enum），
**加原因只改 TS 常量，不需要迁移**。

### 3.3 幂等：两层，缺一不可

```25:27:src/common/idempotency/idempotency.interceptor.ts
 *  1. 用 SET NX PX 抢占 idem:{userId}:{bizId} 占位；抢到 → 执行业务，成功后把结果写回该 key。
 *  2. 抢不到 → 若占位仍是 PENDING，说明上次仍在处理中，返回 409；否则回放上次结果。
```

Redis 层挡秒级重复（结果缓存 24h），`asset_txn.biz_id` 的唯一索引兜持久幂等。
写接口范式固定：

```ts
@Post('xxx')
@Idempotent()
@UseInterceptors(IdempotencyInterceptor)
xxx(@CurrentUser() user: AuthUser, @Body() dto: XxxDto) {
  return this.service.xxx(user.userId, dto);   // service 内用 lock.withLock
}
```

`bizId` 由客户端生成并放在 **body** 里（不是 header），缺失直接 400。

### 3.4 并发：同一玩家的写操作串行化

```ts
return this.lock.withLock(`pet:${userId}`, async () => { ... });
```

繁殖、融合、治疗、训练都动宠物，**必须用同一把 `pet:{userId}` 锁**，
否则「同时融合两组、材料被算两次」这类问题会出现。
拍卖出价用市场侧的锁，已实现。

### 3.5 时间：一律 `ClockService`

孵化倒计时、病症持续时长、活动 `remainSec`、对局过期——
全部 `this.clock.now()`，禁止 `new Date()`，禁止信任客户端时间戳。

### 3.6 实体与迁移

- 列名 snake_case，时间列 `timestamptz`，主键 `bigint`（**pg 下是 string，业务层按 string 处理**）；
- 表结构改动必须 `npm run migration:generate -- src/migrations/Xxx` 再 `migration:run`；
- `synchronize` 永远 false；
- `src/data-source.ts` 用 glob 收实体，**新实体必须放在 `src/entities/*.entity.ts`**，
  否则 `migration:generate` 会把它对应的表判成「多余」并生成 `DROP TABLE`。

### 3.7 管理后台的接入成本

`admin-web` 是 Umi Max + Ant Design Pro，**没有通用 CRUD 脚手架**
（已全量确认：`src/` 下检索 `Crud` / `scaffold` / `GenericTable` / `useCrud` 零命中，
唯一的共享组件是 `components/AvatarDropdown`，与 CRUD 无关）。
每个页面都是 `PageContainer` + `ProTable` + `ModalForm` 的手写组合，典型 150–400 行
（实测区间：`System/Permission` 101 行 ~ `Player` 471 行）。

新增一个后台页面要动 6 处：

1. `admin-web/.umirc.ts` 加路由（构建期必须静态可见；当前是**全平铺**的 23 条路由，无嵌套 `routes`，只有 redirect）
2. `admin-web/src/pages/<域>/<页>/index.tsx` 新建页面
3. `admin-web/src/services/<域>.ts` 新建 API 模块
4. `admin-web/src/types.ts` 加类型
5. `admin-web/src/access.ts` 加 `canReadX / canWriteX`（若需按钮级权限）
6. `⟳ 复核修正` **在 `src/admin/admin-seed.ts` 的 `SEED_MENUS` 追加一条**
   （新权限点再追加 `SEED_PERMISSIONS`），**重启后端**即自动落库

#### `⟳ 复核修正` 第 6 步：是改后端代码，不是手工 SQL

原文写的是「**数据库 `admin_menu` 插一行**」，把它描述成一次手工 DB 操作。**这是错的。**
实测菜单与权限点都由后端代码声明，启动时幂等播种：

```12:12:src/admin/admin-bootstrap.service.ts
import { SEED_MENUS, SEED_PERMISSIONS } from './admin-seed';
```

`AdminBootstrapService.onApplicationBootstrap()` 在 `admin:bootstrap` 分布式锁内跑三件事：

| 步骤 | 行为 | 对新玩法的含义 |
| --- | --- | --- |
| `syncPermissions()` | 按 `code` 插入 `SEED_PERMISSIONS` 里缺失的权限点，**不删除既有** | 新权限点只需追加常量数组 |
| `ensureSuperAdminRole()` | 把 super_admin 的权限**补齐至全量** | **不需要手工插 `admin_role_permission`**，重启自动授权 |
| `seedMissingMenus()` | 按 **`path`** 匹配，只插缺失菜单，**从不更新既有行** | 新页面只需追加 `SEED_MENUS`；但**改名/改排序播种不生效** |

这条链路正在跑，有实测证据：`SEED_PERMISSIONS` 数组 **25 条** ↔ 实库 `admin_permission`
**25 行**；`SEED_MENUS` 数组 **21 条** ↔ 实库 `admin_menu` **21 行**（16 个 `menu` + 5 个 `catalog`）；
`admin_role_permission` 里 super_admin 恰好 **25 条**。三者完全对齐。

由此修正三点原文的结论：

1. **不存在「忘了插菜单行」的风险**——只要 `admin-seed.ts` 改了并重启，菜单必然出现。
   反过来，**只改 `.umirc.ts` 不改 `admin-seed.ts` 才是真正的坑**：页面路由存在，
   侧边栏没有入口，且 `app.tsx` 的 `isPathAllowed()` 会拦掉直连 URL。
2. **开发期不会被权限挡住**。后端 `RolesGuard` 对 super_admin 特判放行，
   前端 `access.ts` 同样 `isSuper` 全放行。新权限点没配给别的角色也不影响自测。
3. `seedMissingMenus()` **只插不改**，所以菜单名写错了不能靠改代码重启修正——
   要走后台「系统管理 → 菜单」页（`PATCH /admin/menus/:id`）或直接改库。
   命名一次定好，比事后改省事。

> 顺带一个已核对的细节：`SeedMenu.type` 联合是 `'catalog' | 'menu' | 'button'`，
> 但 `button` 型在实库里 **0 行**、代码里也没有消费点。
> 想做按钮级权限走 `access.ts` 的 `<Access>`，不要指望菜单表里的 `button`。

**但配置类需求是例外**：「配置中心」(`/config/kv`) 是**注册表驱动的通用 JSON 编辑器**——


> **成本结论**：凡是能塞进 `game_config` 的东西（技巧表、特质表、病症表、稀有度色板、

## 五、P10 · 性格特质（最小改动，与 P0 一起做）

### 数据模型

特质**终身不变**，是宠物身份的一部分，必须落库（不能像 stage 那样派生）。

```
ALTER TABLE pet ADD COLUMN traits jsonb NOT NULL DEFAULT '[]'::jsonb;
```

存 key 数组（`["greedy","sleepy"]`），**不存名称与数值**——那些在配置里，改文案不动数据。

### 新增配置：`pet.traits`

```ts
// src/pet/pet.config.ts
'pet.traits': defineConfig<PetTraitDef[]>({
  description: '性格特质目录：出生随机分配 1~2 个，终身不变。effects 只作用于收益与衰减',
  default: [ /* lively / timid / greedy / aloof / clean / sleepy */ ],
  schema: Joi.array().items(strictObject({
    key: Joi.string().max(24).required(),
    name: Joi.string().max(16).required(),
    desc: Joi.string().max(64).required(),
    weight: posInt.required(),           // 随机权重
    effects: strictObject({
      feedGain: rate, petGain: rate, playGain: rate,   // 互动收益倍率增量
      hungerDecay: rate, cleanDecay: rate, moodDecay: rate,  // 衰减倍率增量
      staminaRecover: rate,
    }),
  })).required(),
}),
'pet.trait_count': defineConfig<{ min: number; max: number }>({ ... }),
```

### 结算接入点

特质效果**必须服务端算**，且要落在既有的两个纯函数上，不新增结算路径：

- **衰减**：`settle()` 已接收 `PetTuning`，把特质聚合成的倍率加进 `PetTuning`，
  影响 `rates.hunger / cleanliness / moodBase / stamina`；
- **互动收益**：`act()` 里 `gain.intimacy/exp/coin` 乘上特质倍率，**再进每日封顶判定**

## 六、P1 · 疾病与治疗

### 6.1 关键设计决策：病症为什么必须落库

原稿的触发条件是「饱食 = 0 **持续 12 小时**」。后端的状态是**惰性派生**的
（`settle()` 从 `last_seen_at` 按速率算，读操作不落库），所以「归零了多久」
其实可以解析地算出来：`zeroSince = last_seen_at + hunger / rate` 小时。

**但治愈状态无法派生**——治好之后饱食度仍是 0，下次请求会立刻重新判定为生病。
所以病症必须持久化，且要记 `since`（前端要显示「已生病 3 天」）。

### 6.2 数据模型

```
CREATE TABLE pet_condition (
  id            bigserial PRIMARY KEY,
  pet_id        bigint      NOT NULL,
  user_id       bigint      NOT NULL,      -- 冗余，避免按 user 查时 join pet
  condition_key varchar(32) NOT NULL,
  since         timestamptz NOT NULL,      -- 服务端判定的起病时刻
  cured_at      timestamptz NULL,
  cured_by      varchar(16) NULL,          -- 'item' | 'clinic' | 'self'
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX uq_pet_condition_active
  ON pet_condition (pet_id, condition_key) WHERE cured_at IS NULL;
CREATE INDEX idx_pet_condition_user ON pet_condition (user_id, cured_at);
```

那条**部分唯一索引是并发防线**：同一只宠物同一种病不可能有两条活跃记录，
即使两个请求同时判定也只有一个能插入成功。

### 6.3 判定时机（重要）

**只在写路径判定，不在读路径写库。** 具体挂在 `PetService` 已有的
`lock.withLock('pet:'+userId)` 内部，即 `feed/bath/pet/play` / `offline/claim` /
`consumables/use` / `cure` 之后。另加一个兜底 cron：

```ts
@Cron('15 * * * *', { name: 'pet-condition-scan', timeZone: 'Asia/Shanghai' })
```

扫「`last_seen_at` 早于 N 小时」的宠物补判——否则纯离线玩家永远不会生病，
而「长期疏于照顾」恰恰是这个玩法的触发前提。

> `GET /pet/conditions` 是**纯读**，只返回 `pet_condition` 的活跃行 + 配置文案，
> 不做判定、不写库。这与 `GET /pet/offline`（只算不发）的处理一致。

#### `⟳ 复核补充` 离线收益是**账号级**的，减益只能取出战宠

这是接 `offlineRate` 时最容易写错的一处，实测源码如下：

```706:713:src/pet/pet.service.ts
    const cappedMs = Math.min(elapsedMs, capMs);
    const cappedH = cappedMs / 3_600_000;

    // 出战宠等级对时薪的小幅加成（level=1 无加成）
    const levelHourly = cfg.coinPerHour * (1 + (level - 1) * cfg.perLevelBonus);
    // 家园舒适度加成：与心情衰减减免同一个系数，上限即 pet.comfort.factorCap
    const coinPerHour = levelHourly * (1 + comfortFactor);
    const claimableCoin = Math.floor(cappedH * coinPerHour);
```

两个关键事实：

1. 时间基准是 **`user.offline_base_at`**（实测 `user` 表确有此列，`timestamptz`），
   是**账号级**的，不是每只宠物各算一份；
2. `level` 取的是**出战宠**（`is_active = true`），没有出战宠才退化到 `id` 最小的一只。

> **因此病症的 `offlineRate` 与 Petpet 的 `offlineRate`（§7.2）只能取出战宠的那一份，
> 绝不能把玩家 6 只宠物的减益累加。** 累加的后果是「多养宠物反而离线收益更低」，
> 而多养宠物是 `pet.max_pets_per_user` 和图鉴 `pet3`/`pet6` 条目在鼓励的行为——
> 两个系统会互相打架，且表现为「玩家觉得数值不对但说不清哪里不对」。
>
> 同理，`GET /pet/conditions` 允许按 `petId` 查任意一只宠物的病，
> 但**只有出战宠的 `offlineRate` 进结算**。这一点要在出参里让前端看得出来，
> 建议加 `affectsOffline: boolean`（= 该宠物是否 `isActive`），省得前端自己推。

```ts
if (dto.price !== undefined) meta.price = dto.price;
if (dto.pool !== undefined) {
  meta.priceAsset = dto.pool === 'marketing' ? MARKETING_POINT : GAME_COIN;
}
```

也就是说**扁平字段的优先级高于 `meta` 里的同名键**。这直接影响 §7.6 建议的通用 JSON 编辑器：

> 运营在 meta 文本域里写 `{"slot":"pet"}` 会被表单的 `slot` 输入框**静默覆盖**，
> 而不是报错。所以那个文本域的定位必须是「**只放没有专属控件的键**」
> （`bonus` / `rarity` / 后续 P8、P12 的新键），并在 UI 上写清楚
> 「`itemType` / `slot` / `price` / `pool` 请用上方表单项，在此填写无效」。
> 这不是可选的文案润色——不写这句，第一次有人在 JSON 里改 `price` 改不动时会当成 bug 报上来。

**缺的只是 `admin-web` 的表单控件**——`ItemDefView` 类型里有 `meta` 字段，
页面上却没有任何对应输入项，只有 `slot`/`price`/`pool`/`comfort`/`gridW`/`gridH`/
`mintLimit`/`sortOrder`/`enabled` 这几个被摊平的固定字段（实测 `Config/Items/index.tsx`
的 `ItemForm` 共 12 个控件，`meta` 与 `rarity` 全库检索零命中）。
另注意 `key` 与 `type` **仅在新建时可填，编辑时不出现**——所以给存量 31 行资产补
`rarity` 只能靠 meta 文本域或迁移，不能靠改 `type`。

所以 P2 的后台改动是**纯前端**，不动后端接口：

| 页面 | 改动 |
| --- | --- |
| 物品管理 → 新建/编辑表单 | `type` 下拉加 `petpet` 选项；加一个通用 `meta` JSON 文本域（复用配置中心那套 `JSON.parse` + 报错提示的写法） |
| 物品管理 → 列表 | 加稀有度色标列（读 `meta.rarity`，取色走 `items.rarities` 配置） |

> **为什么建议加「通用 meta 编辑器」而不是给 `bonus`/`rarity` 各做一个控件**：
> `AssetMeta` 有开放索引签名，后续 P8、P12 还会往里塞字段。
> 每加一个键就改一次表单，是把 jsonb 的灵活性又用硬编码抵消掉。
> 一个 JSON 文本域 + 后端 Joi 兜底，与「配置中心」的取舍保持一致。

三个合规开关仍是**只读展示**，且后端 DTO 里根本没有这三个字段（见 §7.4），
前端不必也不应该为它们做输入控件。

### 9.2 ⚠️ 两个不能照搬的地方

原稿说「异步 PvP 几乎是在现有赛跑上加一层匹配和排行」。方向对，但有两处**必须另写**：

**其一：绝不能复用 `ghostTimes()` 的钳制。** 影子成绩会被夹到玩家自身成绩的
0.7~1.6 倍之间（`clampMin` / `clampMax`）：

```533:534:src/race/race.service.ts
    const lo = playerBase * ghost.clampMin;
    const hi = playerBase * ghost.clampMax;
```

这在单机赛跑里是**对的**——它保证每场比赛都势均力敌、有紧张感。
但在天梯里是**致命的**：一个远强于你的对手会被缩放到只快你 1.6 倍，
弱者也被抬到 0.7 倍，胜负变成掷骰子，积分就没有任何信息量。

> **PvP 的对手成绩必须由对方的 `opponent_snapshot` 按同一套 `race.formula`
> 真实算出，不钳制、不随机填充。** 复用的应该是「完赛时间公式」与前端动画，
> 不是「影子生成器」。

**其二：匹配不要用 `ORDER BY RANDOM()`。** 影子采样这么写是有意的
（注释写明「随机取样而非取最快的 N 条，否则同一批最强成绩会反复出现」），
但它要对整个筛选结果集排序。天梯匹配应走 `pvp_rank` 上的
`idx_pvp_rank_board (season, rank_point DESC, updated_at)`，
按 `rank_point BETWEEN me±matchBand` 取——有序索引扫描，量再大也稳。

观察一段时间再开 `gift` 与 `listing`，最后开 `auction`。

三点前端必须知道的行为：

1. **被拦时是 403 不是 400**，`message` 分别是「交易功能暂未开放」与
   「该交易方式暂未开放」。前端应据此隐藏入口，而不是弹通用错误；
2. **读接口不受开关影响**。`browse` / `my-listings` 任何时候都能调，
   市场关闭时返回的是空列表——所以界面上要能区分「关着」与「开着但没人挂单」
   （后台「挂单管理」页就是为此加了状态横幅，前端也该照做）；
3. **撤单与结算不受开关影响**。`cancel()` 与 `settleAuction()` 都**没有**调
   `assertEnabled`，这是有意的：关市场时已挂的单和已冻结的资产必须还能收尾，
   否则一关开关就把玩家的钱永久冻死。

### 10.4 双向易货：建议不做

原稿的 `/trade/offer` + `/trade/respond`（双方各摆物品 + 币，双方确认成交）
是后端**唯一真正缺失**的交易形态。后端现有的是单向 `gift`（无对价赠送）
和挂单撮合（一价买入 / 竞价）。

**建议不实现**，理由：

1. 挂单 + 赠送已能覆盖 95% 的实际需求（想换东西就各自挂单各自买）；
2. 双向易货需要新表 `trade_offer` + 两阶段确认 + 双方资产双向冻结，
   是所有交易形态里状态机最复杂、最容易出对账不一致的一种；
3. 它是**站外交易（现实货币换游戏物品）最顺手的通道**——
   一价挂单还受 `market.priceBand` 限价约束（防「1 币挂高价物」），
   而双向易货天然绕开限价，因为「对价」是任意物品组合。
   这与 `priceBand` 的设计意图直接冲突。

若业务坚持要做，则必须补：新表 `trade_offer` / `trade_offer_item`、
新 reason `trade_offer` 与 `trade_settle`、双向冻结与超时自动取消 cron，
并且要单独评估限价规则怎么套用。**这是「大」工作量，不是原稿估的「复用」。**

### 13.2 融合：宠物侧需要 3 个新列

```
ALTER TABLE pet ADD COLUMN form   varchar(16) NOT NULL DEFAULT 'normal';  -- normal|glow|rainbow
ALTER TABLE pet ADD COLUMN rarity varchar(16) NOT NULL DEFAULT 'common';
ALTER TABLE pet ADD COLUMN status varchar(16) NOT NULL DEFAULT 'active';  -- active|fused
```

**材料宠物用 `status='fused'` 软失效，不 `DELETE`。**
`race_record.pet_id`、`pvp_match`、`pet_egg.parent_a_id` 都引用宠物 id，
硬删会让历史战报和血统追溯断链。

`⟳ 复核修正` — 「引用」这个词要说准，因为**实测的机制与直觉相反，而真相更支持软失效**。
全库 98 条外键里，指向 `pet.id` 的**只有一条**：

```
pet_equip.FK_3d14a2cdc6ad815a88cc03993fd: FOREIGN KEY (pet_id) REFERENCES pet(id)
```

`race_record` 只有 `user_id → user.id` 的外键，**它的 `pet_id` 是裸 `bigint`，没有任何约束**。
于是硬删的行为分裂成两半：

| 引用方 | 有 FK | 硬删 `pet` 的实际结果 |
| --- | --- | --- |
| `pet_equip.pet_id` | ✅ | 数据库报错拦住——**但仅当该宠有装备记录时** |
| `race_record.pet_id` | ❌ | **静默产生孤儿引用**，不报错、不回滚 |
| `pvp_match` / `pet_egg.parent_*`（本方案新建） | 建议同样不加 | 同上 |

> 所以硬删不是「会被 FK 拦住」，而是**间歇性成功**：没穿装备的宠物删得掉，
> 穿了的删不掉。而删成功的那些会让历史战报指向一个不存在的 id，
> **没有任何一层会报警**。软失效因此不是「为了绕开约束」，
> 而是唯一能保住可追溯性的做法。
>
> 新建 `pvp_match` / `pet_egg` 时也**不要**给 `pet_id` 加 FK：
> 与现状保持一致比局部加固更有价值，混着来会让「哪些删得掉」变得无法预测。

⚠️ **另外这条决定的代价比看上去大，必须提前知道。**
`PetService` 里现在有 **8 处**按 `userId` 查宠物的地方，**全都没有状态过滤**。
最要命的是养宠上限的计数：


其余 7 处是「取出战宠，没有就退化取任意一只」的兜底查询

漏掉任何一处，都可能让一只**已被融合掉的宠物**重新成为当前操作对象。

**实现建议**：不要在 8 个调用点各自加 `status: 'active'`——那正是会漏的写法。

## 十六、P12 · 限时活动

### 16.1 为什么这个要建表而不是塞配置

原稿说「活动是纯配置驱动的」。若只有一个活动、无进度、无领取记录，
确实可以塞进 `game_config`。但实际需要：

- 多个活动并存且各有起止时间 → 要按时间窗口查询；
- 每个玩家的任务进度与领取记录 → 天然是行数据；
- 运营要能在后台**增删改单个活动**，而不是编辑一个巨大的 JSON 数组
  （配置中心是整体 JSON 文本域，改一个活动要重写整个数组，容易误伤）。

所以建表 + 写后台 CRUD 页面。这是本方案里**管理后台工作量最大的一项**。

## 十九、每日封顶与经济口径（后端立场）

原稿多处主张「放开每日封顶」。后端的实际情况与立场：

**事实**：`pet.daily_cap` 实库值 `{"intimacy":100,"exp":200,"coin":500}`，
账号级（多宠共享），实现在 Redis（`cap:{userId}:{day}:{resource}`，TTL 到次日 UTC+8 零点），
`capped` 字段就来自它。**它只作用于 `interact`（四种互动动作）**，
离线收益、赛跑、签到、扭蛋都不受它约束。

**立场**：

1. 要放开是**改配置**，把三个值调大即可，不需要改代码、不需要发版——
   原稿说「要放开得后端改配置，前端改不了」是对的，但这属于运营操作，不属于开发需求；
2. **不建议改成 0 或删除**。它的注释写的是「防刷」，不是「控通胀」——
   它挡的是脚本连点，而脚本连点在任何定位下都该挡；
3. **新玩法的产出天然不受它约束**。封顶的消费点只有一处，就在 `act()` 里，
   且只截断那三个 `gain`：

```291:318:src/pet/pet.service.ts
      const grantedIntimacy = await this.consumeDailyCap(
        userId,
        'intimacy',
        cfg.gain.intimacy,
        day,
        ttlSec,
        t.dailyCap,
      );
      const grantedExp = await this.consumeDailyCap(
        userId,
        'exp',
        cfg.gain.exp,
        day,
        ttlSec,
        t.dailyCap,
      );
      const grantedCoin = await this.consumeDailyCap(
        userId,
        'coin',
        cfg.gain.coin,
        day,
        ttlSec,
        t.dailyCap,
      );
      const capped =
        grantedIntimacy < cfg.gain.intimacy ||
        grantedExp < cfg.gain.exp ||
        grantedCoin < cfg.gain.coin;
```

   发币那一步用的是 `reason: 'interact'`（`pet.service.ts:356`）。
   P4/P11/P13 走各自的 reason（`pvp` / `minigame` / `training`），
   根本不经过这段代码，**所以原稿担心的「小游戏产出被封顶吃掉」不会发生，
   也不需要为此做任何「独立计算」的设计**——它本来就是独立的。

同理，原稿「不设交易手续费与次数限制」的主张已在 §2.3 处理：手续费与风控保留。
