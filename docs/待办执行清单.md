## P0 · 功能性缺口（不修则功能不成立）

### P0-1 封禁全域生效

**现状**
- `assertNotBanned` 仅存在于 `AuthService.login` 与 `PetService`。
- `JwtAuthGuard` 只验签名、不查库；玩家 JWT 有效期 7 天。
- 后果：**账号封禁后，持有存量 token 的客户端仍可正常发奖、扣费、下兑换单**，直到 token 自然过期。这是可被实际利用的漏洞。

**执行项**

- [ ] 选定收口方案（建议两者叠加，理由见下）
  - [ ] `PlayerStatusGuard`：挂在所有玩家端控制器 —— 能拦住不涉及金钱的写操作（如穿戴装扮）
  - [ ] `EconomyService.apply` 内兜底 —— 任何一笔钱都漏不掉，但拦不住纯状态写
  - 单用 Guard 会漏掉未来新增、忘记挂 Guard 的控制器；单用 `apply` 兜底会放过不花钱的写操作。两者叠加：Guard 管准入，`apply` 管资金兜底。
- [ ] 覆盖以下 7 个当前**完全未校验**的可写域
  - [ ] `race`：`start`、`settle`
  - [ ] `daily`：`checkin`、`task/claim`
  - [ ] `boost`：`ad/verify`、`boost/speedup`、`stamina/recover`
  - [ ] `items`：`wardrobe/buy`、`equip`、`unequip`
  - [ ] `home`：`buy`、`place`、`remove`
  - [ ] `dex`：`claim`
  - [ ] `exchange`：`redeem`、`address` 增/改/删
- [ ] 决策：被封禁账号的**读**权限如何处理 —— 建议只封写、保留读（钱包、流水、宠物状态可查），便于客服解释与用户申诉
- [ ] 决策：后台补偿是否豁免 —— `admin_grant` 对封禁账号应仍可执行，否则无法做封号前的结算补偿
- [ ] 决策：封禁后是否主动失效 token（如 Redis 黑名单），还是仅靠请求时查库拦截

**验收**：封禁一个账号后，用其封禁前签发的存量 token 逐个打上述全部端点，应全部返回 403；读接口按上面的决策结果表现一致。

### P0-2 打通配置中心

**现状**
- `game_config` 表存在但 **0 行数据**。
- 全仓库只有 `admin-config.service.ts` 读写该表，**没有任何玩法代码消费它**。
- 真实数值全部硬编码在 6 个 `*.config.ts` 文件中。
- 后果：**运营在后台修改配置，游戏行为不会有任何变化**。配置中心目前是个空壳。

**执行项**

- [ ] 建配置加载层：DB 读取 + 缓存 + **兜底默认值**
  - 兜底是硬要求：DB 缺 key 时必须回落到现有常量，绝不能因为配置缺失导致玩法崩溃
- [ ] 各域改为从加载层取数，逐个迁移：

  | 配置文件 | 需迁移的常量 |
  | --- | --- |
  | `pet.config.ts` | `RATE_PER_HOUR`、`GROWTH`、`ATTRS`、`ACTIONS`、`DAILY_CAP`、`OFFLINE`、`MAX_PETS_PER_USER`、`COMFORT_FACTOR_CAP`、`COMFORT_MAX` |
  | `race.config.ts` | `RACE_TRACKS`、`OPPONENT_COUNT`、`RANK_FACTOR` |
  | `daily.config.ts` | `CHECKIN`、`DAILY_TASKS` |
  | `boost.config.ts` | `AD_REWARD`、`STAMINA_RECOVER`、`SPEEDUP` |
  | `dex.config.ts` | `DEX_ENTRIES` |
  | `exchange.config.ts` | `EXCHANGE_ITEMS` |

- [ ] 灌种子数据：把现有常量的当前值写入 `game_config`（目前 0 行；参考 `item_def` 已灌 10 行的做法）
- [ ] 缓存失效机制：后台改完配置要能生效
  - 注意：PM2 cluster 模式下每个 worker 各持一份缓存，需 TTL 或 Redis pub/sub 广播，否则会出现「部分请求用新配置、部分用旧配置」
- [ ] 配置写入校验：值域与结构校验，避免运营填错把游戏改崩（如把衰减速率填成负数）
- [ ] 决策：哪些配置允许热改、哪些必须重启生效（如 `MAX_PETS_PER_USER` 涉及已有数据）

**验收**：在后台修改任一数值 → 不重启服务 → 对应玩法行为随之改变。
