### P0-1 封禁全域生效 —— ✅ 已完成（2026-08-25）

**原现状**
- `assertNotBanned` 仅存在于 `AuthService.login` 与 `PetService`。
- `JwtAuthGuard` 只验签名、不查库；玩家 JWT 有效期 7 天。
- 后果：账号封禁后，持有存量 token 的客户端仍可正常发奖、扣费、下兑换单，直到 token 自然过期。

**已落地方案（双层）**

- [x] `PlayerStatusGuard`（`src/auth/player-status.guard.ts`）：管准入，只拦写方法，`GET/HEAD/OPTIONS` 放行
- [x] `PlayerStatusService`（`src/auth/player-status.service.ts`）：账号状态校验的唯一出口，由 `AuthModule` 导出
- [x] `EconomyService.apply` 资金兜底：把「账号未封禁」并入余额变更的那条原子 `UPDATE`，绕过守卫的内部调用同样动不了钱
- [x] `PetService.assertNotBanned` 改为委托 `PlayerStatusService`，消除重复实现

> 为什么守卫依赖服务而不是直接注入 `UserRepository`：Nest 在**使用方模块**的注入器里实例化守卫。
> 守卫若直接依赖仓储，每个挂载它的模块都得自己 `TypeOrmModule.forFeature([User])`；
> 依赖 `AuthModule` 导出的服务则零改动，因为各玩法模块本来就已经 import 了 `AuthModule`。

**覆盖范围**：9 个控制器、12 处 `@UseGuards` 挂载点、**28 个写端点**。
比原清单多出 3 个此前漏列的：`POST /ad/token`、`POST /race/reward/double`、`POST /race/revive`。

**已定决策**
- 封禁**只封写、保留读**：钱包、流水、宠物状态仍可查，便于客服解释与用户申诉
- 后台补偿**豁免**：`admin_grant` / `admin_deduct` / `compensation` 三个原因不受封禁拦截，否则无法做封号后的结算与违规追回
- **不做 token 黑名单**：每次写请求查一次库（主键命中）。封禁是安全控制，加缓存会引入「已封禁仍放行」的窗口，而写请求本身必然要打库，多这一次开销可忽略

**验收结果**（冒烟脚本已跑过并删除，永久回归由单测承担）
- 正常账号 28 个写端点：误拦 **0**
- 封禁后同一存量 token 打 28 个写端点：全部 403，漏网 **0**
- 封禁后 13 个读端点：误封 **0**
- 经济域四条路径：封禁发放被拒 / 后台补偿放行 / 后台追回放行 / 解封后恢复，全部符合预期
- 新增 3 个常驻单测覆盖封禁与豁免分支

### P0-2 打通配置中心 —— ✅ 已完成（2026-08-26）

**原现状**
- `game_config` 表存在但 0 行数据；全仓库只有 `admin-config.service.ts` 读写该表，没有任何玩法代码消费它。
- 真实数值全部硬编码在 6 个 `*.config.ts` 文件中。运营在后台改配置，游戏行为不会有任何变化。

**已落地方案**

*可调边界：数值可调，结构不可调*

开放给运营的是「数值」；决定代码分支或历史数据口径的取值留在代码里，因为改它们不是调参而是改语义：

| 留在代码里 | 原因 |
| --- | --- |
| `STAT_MIN` / `STAT_MAX` | DTO 与前端进度条按 0~100 呈现，属结构约束 |
| `BUSINESS_TZ_OFFSET_MS` | 改了会让已落库的业务日键口径漂移 |
| `AD_SCENES` | 每个 scene 对应一条具体兑换代码路径 |
| `daily.tasks[].source` / `dex.entries[].type` | 枚举值各对应一条统计实现，故只在 schema 内收口为已实现的取值 |

*四层结构*

1. **声明**：配置项声明在各自的域文件里（`src/<域>/<域>.config.ts` 的 `PET_CONFIG` / `RACE_CONFIG` / …），每项含 `default` + Joi `schema` + 运营可读 `description`。新增一个可调值只改对应域文件。
2. **汇总**：`src/config/game-config.registry.ts` 合并成总注册表并派生 `ConfigShape`（key → 值类型），使取值有类型安全。
3. **加载**：`src/config/game-config.service.ts`（`@Global()` 模块，与 `RedisModule` 同处理）。
4. **写入**：`admin-config.service.ts` 改为按注册表校验 + 写后失效缓存。

*加载层的三条硬约束*

- **永不因配置问题抛错**。DB 挂了 / 行缺失 / 值非法都回退默认值并告警。
- **加载时二次校验**。写入已校验，但直连 SQL 改库绕得过去；取值时按 schema 再验一遍，且**单项非法只回退该项**，不影响同批其它 key。
- **请求内配置一致**。调用方取一次 `snapshot()` 往下传，避免一个请求内前后读到不同版本。

*配置项清单（21 项，全部支持热改）*

| 域 | key |
| --- | --- |
| pet | `pet.rates`、`pet.growth`、`pet.attrs`、`pet.stages`、`pet.actions`、`pet.daily_cap`、`pet.max_pets_per_user`、`pet.offline`、`pet.comfort` |
| race | `race.tracks`、`race.opponent_count`、`race.revive`、`race.rank_factor` |
| daily | `daily.checkin`、`daily.tasks` |
| boost | `boost.ad_reward`、`boost.stamina_recover`、`boost.speedup`、`boost.ad_token` |
| dex | `dex.entries` |
| exchange | `exchange.items` |

*关键决策与理由*

- **粒度**：一个 key 对应一组常量，value 存整个 JSON。契合既有 `jsonb value` 列与后台 CRUD，21 个 key 而非 80 个散值。
- **校验用 Joi**：项目已用它校验环境变量，不引新依赖。schema 同时守住值域（速率非负、`growth.ratio ≥ 1`、`comfort.factorCap ≤ 0.9`）、禁止未知字段（防运营拼错字段名后静默失效）、跨字段约束（签到 `maxCoin` 不得低于 `baseCoin`）。
- **缓存**：整表一次查询 + 30s TTL + 写后失效，无 Redis pub/sub。当前 PM2 `instances: 1`，写后失效即时生效；将来扩多实例时最坏 30s 收敛，代价小于引入 pub/sub 与额外连接。
- **`invalidate()` 只置标记、不丢快照**。单测发现的缺陷：丢快照会让「刚失效 + DB 恰好不可用」把配置静默跌回代码默认值（奖励、上限突变），比读到略旧的值危险得多。
- **注册项禁止 DELETE**，改用 `POST /admin/config/:key/reset` 恢复默认。删掉只会让它从后台列表消失、运营再也调不到，而玩法照旧走默认值，是纯误操作。DELETE 仅保留用于清理未注册的历史遗留 key。
- **写入只接受注册过的 key**。否则运营打错一个字就存出一条永不生效、也无任何报错的「幽灵配置」。
- **放开 3 个 DTO 的模块级 `@IsIn` 白名单**（`race.trackKey`、`daily.taskKey`、`dex.entryKey`）：白名单在模块加载时快照，会让后台新增的赛道/任务/图鉴条目永远校验不过。改为服务层按当前配置判定未知 key。`boost` 的 `AD_SCENES` 属结构性取值，保留 `@IsIn`。

*接口变化（后台）*

- `GET /admin/config`：响应新增 `registered`（是否代码注册项）、`default`（内置默认值）、`modified`（是否已偏离默认值）三个字段，便于运营看出改了什么、能否恢复。
- `POST /admin/config/:key/reset`：新增，恢复默认值。
- `PUT /admin/config/:key`：非法值或未注册 key 返回 400 并带具体原因（原先任意 JSON 都能写入）。
- `DELETE /admin/config/:key`：注册项返回 400。

### A. 确认有缺陷，需要动手（4 项）

- [ ] **A1 · 后台履约并发（资损）**：`AdminExchangeService.ship()` 与 `cancel()` 都是「`findOne` 读状态 → 改字段 → `save()` 整实体」，两者并发时**互不阻塞、都返回成功**。实测（`scripts/p2-verify-fulfillment.js`，复现 3/3）：点发货的运营拿到 `200 status=shipped` 会去仓库发货，同时取消方退了积分、状态改回 `cancelled`、`tracking_no` 被后写的整实体 save 覆盖成 null —— **实物发出 + 积分退回，且库里查不到发货痕迹**。
      修法（与仓库既有惯例一致）：把状态流转改成条件更新并检查影响行数，`UPDATE redeem_order SET status='shipped' WHERE id=$1 AND status='pending'`，affected=0 即抛 400。`EconomyService` 与 `RaceService.settle` 已经是这个写法。
      注：**并发双取消不会退两次钱**，靠的是 ledger 的 `(user_id,biz_id,pool)` 唯一键（`refund:{orderId}`），不是那个不可靠的状态判断 —— 修的时候别把这层去掉。
- [ ] **A2 · `POST /ad/verify` 不校验广告凭证**：`AdVerifyDto` 只有 `bizId` + 可选 `scene`（注释写「仅记录用」），`BoostService.verifyAd()` 里没有任何 `AdTokenService` 调用。客户端持 JWT 直接循环调用即可拿满每日广告币（默认 30 币 × 5 次 = 150 币/天），**根本不需要看广告、也不需要先领 nonce**。
      同一份代码里赛跑增值（`/race/reward/double`、`/race/revive`）却强制 `adToken` 并走 Lua 原子核销 —— 两套端点风控强度不一致，是漏改而非设计。
      修法：`/ad/verify` 与赛跑增值对齐，要求 `adToken` 并 `consume(userId, adToken, scene)`。日上限 5 次的量级不大，但这是「客户端说看了就给」的信任模型，上线后是被脚本刷的第一个口子。
- [ ] **A3 · 舒适度不影响离线产出**：`computeOffline()` 只吃 `offline_base_at`、等级、`pet.offline` 配置，**不读 `HomeStat`**。而规格 §舒适度写的是「①减缓 mood 衰减 ②提升离线产出」，切片 4 也写了「舒适度回流 mood/离线」。玩家现象：摆满家具后 mood 明显掉得慢，但离线收益一分不变。
      二选一：把 comfortFactor 接进 `computeOffline`，或把规格里「②提升离线产出」删掉。**这是数值设计取向，需要拍板**（家具已经通过 mood 间接影响产出，再直接加成会不会过强）。
- [ ] **A4 · admin-web 配置页**：`pages/Config/Kv/index.tsx:136` 用 `rowKey="id"`，而后端 `ConfigListItem` 根本没有 `id` 字段（只有 `key`）—— 每行的 React key 都是 undefined。同时未用上 `registered`/`default`/`modified` 三个字段，也没有 reset 按钮，且对已注册键仍展示「删除」（点了必被后端 400）。
      好消息：`PUT` 返回 400 时**能**看到 Joi 的具体报错，靠的是 `app.tsx` 的全局 errorHandler 读 `data.message`，不是页面级 try/catch。

### B. 需要你拍板后再决定（4 项）

- [ ] **B1 · 兑换库存 / 限购**：清单原文写的「`redeem_order` 与 `exchange_item` 库存扣减是否原子」，前提不成立 —— `exchange_item` 表不存在（目录早已迁到 `game_config`），`ExchangeItem` 也没有 `stock` 字段。所以不是「会不会超兑」，而是**没有任何库存与限购**：积分够就能无限兑同一件实物（实测同一项连兑 7 单无拦截）。

- [ ] **B2 · 定时对账作业**：全仓 `@Cron`/`@Interval`/`@Timeout`/`SchedulerRegistry` **零匹配**，`ScheduleModule.forRoot()` 引入了但没人用（空载依赖）。`ecosystem.config.js` 注释提到的 `isCronWorker` 守卫在代码里也不存在。

      需运营拍板：提价 / 扩目录 / 加重复消耗型 sink（消耗品、抽奖）/ 把兑换中心部分虚拟商品改成 game 池。

### C. 已确认无问题，仅记录结论（3 项）

- [x] **C1 · 离线封顶**：担心的「信客户端申报」不存在 —— `OfflineClaimDto` 只有 `bizId`，且全局 `forbidNonWhitelisted` 会把多传字段直接 400，时长完全由 `offline_base_at → now` 推导。CAP 在预览和领取里各算一遍（领取不信预览）。领取后基准前移，换新 bizId 再领得 400 —— 双保险，不只靠幂等键。e2e 已固化 3 例。
      **顺带修正一处过时注释**：`user.entity.ts:45-46` 写「`elapsed = min(客户端申报, now − last_seen_at)`」，与实现不符，应以 `computeOffline` 为准（已列入 P1-4 文档同步）。
      已知瑕疵（低概率、非 CAP 逻辑问题）：发币与推进基准不在同一事务，若 `users.save` 失败会留下「币已发、基准未推进」，此时客户端**换新 bizId** 重试可双发。正常客户端会用同一 bizId 重试（经济层幂等安全）。
- [x] **C2 · 赛跑公平性**：得分 = `powerOf(speed, endurance) × 随机(0.9~1.1)`，`power = speed×2 + endurance`，三围纯等级派生（`10 + 1.0×(lv−1)` / `10 + 0.8×(lv−1)`）。`getBattleStats` 不查 `pet_equip`，装扮零加成（e2e 已固化：戴上小皇冠后战力与体力上限不变）。名次在 `POST /race/start` 服务端算定并落库，`settle` 只发预存的 `rewardCoin`，DTO 无 score/rank 入参，客户端无法影响判定。对手强度 = `power × 赛道难度 × 随机(0.8~1.05)`，相对玩家缩放。
      随机源是无种子 `Math.random()`，不可复现 —— 客服要复盘某一场比赛时只能看落库的 `score`/`rank`，无法重算验证。目前可接受（记录已足够），若将来要「回放/申诉」能力，需改成 raceId 派生的确定性 PRNG。
- [x] **C3 · 假登录开关**：生产环境是**强制失效**，不是只靠日志。三层：①`env.validation.ts` 的 Joi `.when('NODE_ENV', {is:'production', then: Joi.valid(false)})` —— 生产开着直接**启动失败**；②`configuration.ts` 里 `mockLogin` 由 `WECHAT_MOCK_LOGIN==='true' && NODE_ENV!=='production'` 双条件推导，即使绕过 Joi 也恒为 false；③`WechatService.mockSession()` 在开关关时抛 401「假登录未启用」，明确**不回落**真实微信请求。日志告警只在非生产且开关开启时打印。
      残留注意：`NODE_ENV=staging` 时开关仍可开启 —— 若 staging 接公网需运维管控。
