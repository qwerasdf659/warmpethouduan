# 〇、后端实际现状（真实代码 + 真实数据库核对结果）

## 0.1 技术体系（权威，不可被前端需求改变）

| 项 | 现状 |
| --- | --- |
| 框架 | NestJS 11 + TypeScript 5 + Node 22，监听 `0.0.0.0:8080` |
| 持久层 | PostgreSQL 16（Sealos 托管）+ TypeORM，`synchronize:false`，**表结构只走 migration** |
| 缓存/锁 | Redis 7（本机，`ioredis`，`REDIS_CLIENT` 注入） |
| 鉴权 | `@nestjs/jwt`，`Authorization: Bearer <jwt>`，payload `{ sub, openid }` |
| 全局管道 | `ValidationPipe({ whitelist, forbidNonWhitelisted, transform })`（多传字段直接 400） |
| 路由前缀 | **无全局前缀**，控制器直接挂 `/auth`、`/pet` … |
| 主键 | `bigint` 自增，pg 驱动下**以字符串返回**，业务层按 string 处理 |
| 列命名 | 数据库 **snake_case**（`@Column({ name: 'last_seen_at' })`），JSON 出参 **camelCase** |
| 时间 | 一律 `timestamptz`（UTC）；服务端权威时钟 `ClockService.now()`；结算基准存 `pet.last_seen_at` |

## 0.2 已实现的接口（源码实测 · 2026-08-25 复核）

**玩家端**

| 接口 | 方法 | 入参 | 出参 | 说明 |
| --- | --- | --- | --- | --- |
| `/auth/login` | POST | `{ code }` | `{ token, userId }` | code2session → 查/建 user → 自签 JWT；**登录即刷新 `user.last_seen_at`** |
| `/pet/state` | GET | `?petId=`（可选） | `{ pet }` | 惰性结算后的状态；省略 `petId` 取 active 宠，无宠则自动建一只 |
| `/pet/list` | GET | Bearer | `{ pets: [...] }` | 我的全部宠物（逐只结算，只读不落库） |
| `/pet/create` | POST | `{ bizId, nickname?, species? }` | `{ pet }` | `@Idempotent()` + 玩家锁；上限 6 只，首只自动 active |
| `/pet/active` | PUT | `{ petId }` | `{ pet }` | 切换出战宠；库层部分唯一索引保证至多一只 active |
| `/pet/feed` | POST | `{ bizId, petId? }` | `ActionResult` | hunger +30，冷却 30s |
| `/pet/bath` | POST | 同上 | `ActionResult` | cleanliness +40，冷却 60s |
| `/pet/pet` | POST | 同上 | `ActionResult` | mood +15，冷却 20s（抚摸/梳毛） |
| `/pet/play` | POST | 同上 | `ActionResult` | mood +20、stamina −10，冷却 60s；体力不足 400 |
| `/wallet` | GET | Bearer | `{ wallet: { gameCoin, marketingPoint } }` | 无钱包自动建行返 0 |
| `/wallet/ledger` | GET | `page`/`pageSize`/`pool?` | `{ list, total }` | 积分流水倒序分页 |

- `pet` 出参（camelCase）：`id, nickname, species, isActive, hunger, cleanliness, mood, stamina, staminaMax, intimacy, level, exp, expIntoLevel, expToNext, stage, speed, endurance, lastSeenAt`。
- `ActionResult` = `{ pet, gained:{intimacy,exp}, capped, levelUp, cooldownRemainMs }`。
- 四个互动动作均 `@Idempotent()` + `lock.withLock('pet:'+userId)`；冷却中返回 **429**，体力不足 **400**，`petId` 不存在或不属于本人 **404**。
- 衰减/恢复：`hunger −5/h`、`cleanliness −3/h`、`stamina +10/h`；**mood 为派生量**（基础 −2/h，饱食度或清洁度触底后的那段时长再额外 −3/h，整体 ×(1−comfortFactor)）。全部数值集中在 `src/pet/pet.config.ts`。
- `staminaMax / speed / endurance` **不落库**，由 `level` 按成长曲线派生（见 §2.1 注）。
- `PetService.peekPets(userId)` 只读、**不建宠**，供后台查询，与玩家端同一套结算。

**后台端（RBAC + 审计，已落地）**——独立 `typ:'admin'` JWT；`/admin/*` 受 `AdminJwtAuthGuard + RolesGuard`（`@RequirePermissions()`）保护；写操作经 `@Audit()` + `AdminAuditInterceptor` 落 `admin_audit_log`。管理员口令为 **scrypt** 散列。

| 接口 | 方法 | 权限 | 出参 |
| --- | --- | --- | --- |
| `/auth/admin/login` | POST | 公开 | `{ token, profile{id,username,displayName,roles[],permissions[],menus[]} }` |
| `/auth/admin/me` | GET | 登录 | `profile` |
| `/admin/admin-users`（`:id` GET/PATCH/DELETE、`:id/roles` PUT、`:id/password` PUT） | GET/POST/... | admin:read / admin:write | 列表 `{ list, total }` / 资源 JSON |
| `/admin/roles`（CRUD + `:id/permissions` PUT + `:id/menus` PUT） | GET/POST/PATCH/DELETE/PUT | role:read / role:write | 资源 JSON |
| `/admin/permissions`（列表/建/删） | GET/POST/DELETE | permission:read / permission:write | 资源 JSON |
| `/admin/menus`（列表/建/改/删） | GET/POST/PATCH/DELETE | menu:read / menu:write | 资源 JSON |
| `/admin/audit-logs` | GET | audit:read | `{ list, total }` |
| `/admin/players`、`/admin/players/:id` | GET | player:read | `{ list, total }` / **`{ player, pets: [...] }`**（多宠，`player` 含 `lastSeenAt`） |
| `/admin/idempotency?userId=&bizId=` | GET | player:read | 幂等记录（Redis 扫描） |

> 后台响应同为**纯 HTTP 语义**（资源 JSON / 失败 `{code,message}`）；分页统一 **`{ list, total }` + query `page`/`pageSize`**（`PaginationDto`）。

# 〇·六、架构决策（已拍板 · 2026-08-25）

> 前提：**未上线、可一次性投入、不兼容旧接口、以长期低维护成本与低技术债为准**；技术栈 = NestJS + PostgreSQL（单库）+ TypeORM + Redis。以下为最终结论，后续所有设计以此为准。

| # | 决策项 | 结论 | 关键理由 |
| --- | --- | --- | --- |
| 1 | 钱包 / 账本模型 | **余额表 `wallet` + 单边流水账本 `ledger`（`(user_id,biz_id,pool)` 唯一）**；MVP 不做冻结/在途(escrow) | 单机内闭环、无对手方结算，不上银行式复式双录；流水+余额快照足够对账与追溯。**已落地**，幂等键带 `user_id` 防跨玩家串账（见 §6.2） |
| 2 | 接口响应格式 | **纯 HTTP 语义**：成功直接返回资源 JSON，失败 `{ code, message }`（`code`=HTTP 状态码） | 最标准、后端零封套、工具/网关/监控天然识别；全项目统一、禁止再混用（现状混用是要根治的债） |
| 3 | API 前缀 / 版本 | **保持无全局前缀**（沿用现状 `/pet`、`/auth`…） | 按拍板 |
| 4 | 宠物建模 | **多宠 / 多存档，现在就做**：去掉 `pet.user_id` 唯一约束，`pet.id` 作为所有宠物级子系统外键 | 未上线是改建模的唯一零成本时机；一切宠物级数据挂 `pet_id` 而非 `user_id` |
| 5 | 静态数值配置 | **已落地**：目录型数据用 DB 表 `*_def`（`item_def`）；玩法数值用 `game_config` KV（jsonb）+ `GameConfigService` 加载层（DB 优先、代码常量兜底、30s 缓存 + 写后失效）。**数值可调、结构不可调**；MVP 不做版本/定时生效 | 运营要频繁调数值，杜绝硬编码技术债；但决定代码分支与历史数据口径的取值（状态上下界、日切偏移、广告 scene、进度来源枚举）留在代码里——改它们不是调参而是改语义。详见 §6.6 |
| 6 | 激励广告校验 | **服务端一次性 `nonce`（绑 `bizId`、短 TTL）+ 频控/次数上限 + 保底 + 风控日志** | 微信小游戏拿不到可靠服务端广告回执，安全来自频控+幂等+风控而非平台背书 |
| 7 | 金额数值类型 | **`bigint` 整数计数**（无小数） | 禁用浮点，避免累积误差 |
| 8 | 幂等落地 | **经济写操作以 `uq_ledger_user_biz_pool` DB 唯一约束为权威 + Redis 结果缓存**；非经济（冷却/上限）仅 Redis | 钱相关不能只靠缓存（Redis 幂等结果只存 24h） |
| 9 | 主键 / ID | **内部 `bigint` 自增 + 对外幂等用客户端 `bizId(UUID)`** | 单库无需 Snowflake，避免过度设计 |
| 10 | 拥有物模型 | **通用 `item_owned`（含 `count`）+ `item_def`（type 分类）** | 新增品类零改表；装扮唯一拥有、家具可多件 |
| 11 | 时区 / 日切 | **UTC 存储（timestamptz）+ 业务日切按 `Asia/Shanghai` 00:00** | 签到/任务/每日上限统一东八区 |

## 多宠归属划分（子系统挂 `user_id` 还是 `pet_id`）

| 层级 | 子系统 |
| --- | --- |
| **账号级（挂 `user_id`）** | 钱包（gameCoin/marketingPoint）、账本 `ledger`、签到 / 每日任务、图鉴、**装扮 & 家具的拥有权**、**家园布置**（一个家所有宠物共用，`comfortFactor` 效果作用到每只宠物） |
| **宠物级（挂 `pet_id`）** | 状态数值（hunger/mood/cleanliness/stamina/intimacy）、成长（level/exp/三围 speed·endurance）、赛跑记录、**装扮穿戴**（每只各穿各的） |
| **账号发放 + 宠物结算** | 离线产出（每只宠物按自身状态结算衰减，被动 gameCoin 汇总入账号钱包并封顶） |

## 经济模式（★与原稿不同，以此为准）

- **不跳任何外部小程序**（原「跳天工小程序」设定作废）。**小游戏自身发放礼品，含实物 + 虚拟**，兑换与实物履约在游戏内闭环完成。
- **双池用途与合规红线**：
  - `gameCoin`（玩游戏产出：照顾/赛跑/签到/离线/广告）：**纯虚拟闭环**，只换装扮/家具/加速；**不可兑实物**（守住「网游虚拟货币不得反向兑换财物」红线，防套现）。
  - `marketingPoint`（来自**线下扫码 / 异业消费**等营销触点）：**可在游戏内兑换实物 + 虚拟礼品**（落在「营销/会员积分兑礼」合法框架内）。
  - 两池物理隔离、永不互转。
- **实物兑换履约子系统（本期建完整）**：收货地址、兑换订单、发货 / 核销状态、库存、对账。实物涉及履约/售后/税务/未成年人消费等合规，上线前建议过法务。

# 一、后端权威通用约定（每个新接口都遵循）

1. **鉴权**：除 `/auth/login` 外所有接口需 `Authorization: Bearer <jwt>`；控制器用 `@UseGuards(JwtAuthGuard)` + `@CurrentUser()` 取 `{ userId, openid }`。
2. **服务端权威**：状态值、赛跑结果、奖励数额、离线时长全部后端算；客户端传值仅作表现。时间统一 `ClockService.now()`。
3. **不信任客户端时钟**：离线/时差结算 `elapsed = min(客户端申报, now − user.last_seen_at)`，再 `min(elapsed, CAP)`。
4. **幂等**：所有「发奖/扣费/看广告发奖」写接口 `@Idempotent() + IdempotencyInterceptor`，**`bizId` 放请求体**，DTO 用 class-validator 校验（参考现有 `PetActionDto`）。经济域再叠加 `uq_ledger_user_biz_pool` **DB 唯一索引**做持久强去重（Redis 结果缓存只有 24h，钱相关不能只靠缓存）。
5. **并发安全**：同一玩家写操作包在 `lock.withLock('pet:'+userId, …)`（或域内更细粒度锁）里串行化。
6. **软失败不死亡**：广告校验失败给保底小额、记录风控，不阻断主链路。
7. **积分双池物理隔离**：`gameCoin`、`marketingPoint` 分列/分账本，接口层禁止互转。
8. **响应格式**：成功→资源 JSON（沿用 `{ pet }` 这种域包裹风格）；失败→`{ code, message }`；时间 ISO8601(UTC)；id 为 string。
9. **静态配置入库（已落地）**：运营数值一律不硬编码在业务代码里。两条通道：
   - **目录型数据**（商品/家具/兑换品）→ `*_def` 表（`item_def`），玩家侧只读引用其 id。
   - **玩法数值**（衰减速率、成长曲线、每日上限、赛道、任务、图鉴、广告参数）→ `game_config` KV + `GameConfigService` 加载层，共 **21 个 key**。
   写玩法代码时的规矩：
   - **取值只走 `GameConfigService`**，禁止再 import 数值常量。域内 `*.config.ts` 的常量已降级为「默认值 + 兜底」，只在注册表里被引用。
   - **一次请求取一次快照往下传**（`snapshot()` → 打包成 `PetTuning` 这类对象作显式入参），不要在每个私有方法里各读一次；否则同一次请求可能前后读到不同版本的配置，算出自相矛盾的结果。这也让 `settle()`/`levelOf()` 这类纯计算保持同步、可单测。
   - **新增可调值**：在对应域的 `*.config.ts` 里加一条 `defineConfig({ description, default, schema })` 即可，注册表自动收录、启动种子自动灌入、后台自动可见。schema 必须真正收住值域（速率非负、比率 ≥1、禁止未知字段），它是运营误填时唯一的拦截点。
   - **数值可调，结构不可调**：决定代码分支或历史数据口径的取值不要开放（状态上下界、日切偏移、广告 scene、任务/图鉴的进度来源枚举）——改它们不是调参而是改语义。
   - **配置问题绝不能让玩法崩**：加载层对 DB 故障、缺 key、脏数据一律回退默认值并告警，且单项非法只回退该项。写新配置项时务必保证**默认值本身合法**（有单测断言这一点）。
10. **表结构改动必须新增迁移**：`migration:generate → migration:run`，禁用 synchronize。`src/data-source.ts` 的 `entities` 用 glob（`src/entities/*.entity.ts`）——**新增实体禁止只登记到 `app.module.ts`**，否则 `migration:generate` 会把该实体对应的表当「多余表」生成 `DROP TABLE`。生成迁移后**必读一遍 SQL**，确认没有意外的 `DROP`。
11. **关键不变量下沉到库层**：应用层锁只防本进程/正常路径，DB 约束才是最终防线。已落地示例：`uq_pet_active_per_user` 部分唯一索引（每人至多一只出战宠）、`uq_ledger_user_biz_pool` 唯一索引（记账幂等）、`ck_wallet_non_negative` CHECK（余额不为负）、`wallet`/`ledger` 外键（不许给不存在的玩家记账）。
12. **经济写操作不加 Redis 锁**：并发正确性由「单语句原子 `UPDATE … WHERE col + delta >= 0`」+ 唯一索引保证。Redis 锁不可重入，宠物域持锁时调 `EconomyService.apply` 若再抢锁会自死锁（详见 §6.2）。
13. **分页约定（已落地）**：列表接口入参 `page`/`pageSize`（`PaginationDto`，已上提到 `src/common/dto/`，玩家端与后台共用同一实现），出参 **`{ list, total }`**；玩家侧新接口一律沿用此形，前端适配（原稿的 `{ items, nextCursor }` 作废）。
14. **后台鉴权隔离（已落地）**：后台走 `/auth/admin/login` 签发 `typ:'admin'` JWT，`/admin/*` 用 `AdminJwtAuthGuard + RolesGuard + @RequirePermissions('xxx:read|write')`，与玩家侧 `/auth`、`JwtAuthGuard` 物理隔离；写操作加 `@Audit()` 落审计。

> 三围即 `level` 的纯函数——落库属冗余，且调曲线时存量行会与新曲线不一致（数据漂移），还要额外写回刷全表。

> 若将来出现「道具/训练带来的永久属性加成」，再单独加 `pet_attr_bonus` 加成列/表，不回头改这三列。

**mood 派生规则**（已实现于 `PetService.settle`）：

```
elapsedH        = (now − last_seen_at) / 1h
hungerZeroH     = hunger / 5            # 饱食度触底所需小时
cleanZeroH      = cleanliness / 3       # 清洁度触底所需小时
starvingH       = max(0, elapsedH − min(hungerZeroH, cleanZeroH))
moodDecay       = (2 × elapsedH + 3 × starvingH) × (1 − comfortFactor)
mood            = clamp(mood − moodDecay, 0, 100)
```

> 关键点：额外惩罚**只作用于真正处于「饿/脏」状态的那段时长**，而不是「结算完发现触底就整段罚」。
> 例：离线 24h、初始 hunger=80/cleanliness=80/mood=100 → hunger 16h 时触底，starvingH=8，
> moodDecay = 2×24 + 3×8 = 72 → mood=28（已冒烟验证）。

## 2.2 惰性结算（已实现）

# 六、双积分账户（经济地基 · **已落地**）

> 换装/家园/兑换都依赖钱包与账本，故经济域先建。已落地为 `src/economy/` 模块（迁移 `EconomyWalletLedger`）。

## 6.1 两池

| 池 | DB 列 | 来源 | 去向 | 红线 |
| --- | --- | --- | --- | --- |
| 游戏币 | `wallet.game_coin` | 照顾/赛跑/签到/离线/广告（玩游戏产出） | 换装、家具、加速（纯虚拟） | 不可充值/提现/换现金；**不可兑实物**（防反向兑换套现） |
| 营销积分 | `wallet.marketing_point` | 线下扫码 / 异业消费（营销触点） | **游戏内兑换实物 + 虚拟礼品** | 与游戏币物理隔离，永不互转；实物兑换须走履约/对账 |

> 无外部小程序跳转，兑换全在游戏内闭环（见十三）。`gameCoin` 守「网游虚拟货币不得反向兑换财物」红线；`marketingPoint` 因来源是消费/营销，兑实物落在合法营销积分框架。

## 6.2 账本（单边流水，非复式双录）

所有变动走 `ledger`：一行 = 「某玩家某池的一次变动」，带 `balance_after` 余额快照便于逐笔回溯。
**不做银行式复式双录**——单机内闭环、无对手方结算，复式属过度设计（对齐 §0·六 决策 1）。
余额快照在 `wallet`，权威可由 `sum(ledger.delta)` 对账（冒烟已验证两者恒等）。

唯一写入口：`EconomyService.apply({ userId, pool, delta, bizId, reason, refId? })`。业务代码**禁止直接改 `wallet`**。

**并发与幂等不靠 Redis 锁，靠数据库**，这是本模块最关键的设计：

| 关注点 | 手段 |
| --- | --- |
| 并发扣减不超卖 | 单语句 `UPDATE wallet SET col = col + $delta WHERE user_id=$1 AND col + $delta >= 0`，原子完成「校验+变更」；余额不足表现为**影响 0 行** → 400 `余额不足` |
| 重复提交 | `uq_ledger_user_biz_pool (user_id, biz_id, pool)` 唯一索引；冲突（23505）→ 事务回滚（余额变更一并撤销）→ 幂等回放，返回**首次**账目 + 当前余额 + `duplicated:true` |
| 余额永不为负 | 库层 `ck_wallet_non_negative` CHECK 兜底 |
| 池合法性 / 空变动 | 库层 `ck_ledger_pool`、`ck_ledger_delta_nonzero` CHECK |
| 脏 userId | `wallet.user_id`、`ledger.user_id` 外键指向 `user(id)`（NO ACTION：有资金流水的玩家不许硬删，业务上用封禁） |

> **为什么刻意不加 Redis 锁**：Redis 锁**不可重入**。宠物域的写操作已持有 `pet:{userId}` 锁，
> 后续「离线领取/赛跑结算」会在锁内调 `apply` 发币；若 `apply` 再抢同一把锁必然自死锁，
> 抢另一把锁则引入锁顺序问题。把正确性交给数据库的原子语句 + 唯一索引，调用方可在任意锁上下文里安全调用。

> **幂等粒度为什么带上 `user_id` 和 `pool`**：只用 `biz_id` 全局唯一时，两个玩家撞同一个 `bizId`
> 会被误判重复，进而把**别人的账目**回放给当前玩家（串账 + 信息泄露）。带上 `pool` 则允许一次操作最多各动一次两个池。

> **单次调用只动一个池**。目前没有需要同时动两池的场景；真出现时应新增显式的多池事务方法，
> **不要连调两次 `apply`**（那样不是原子的）。

## 6.3 接口（已实现）

| 接口 | 方法 | 入参 | 返回 | 现状 |
| --- | --- | --- | --- | --- |
| `GET /wallet` | GET | Bearer | `{ wallet: { gameCoin, marketingPoint } }`（无钱包则自动建行返 0） | ✅ |
| `GET /wallet/ledger` | GET | `page`/`pageSize`/`pool?` | **`{ list, total }`**（倒序） | ✅ |

- 流水条目字段：`id, pool, delta, balanceAfter, bizId, reason, refId, createdAt`。
- 分页沿用全项目约定 `{ list, total }`（原稿 `{ items, nextCursor }` 作废，见 §一.12）。
- **没有通用的发放/扣减写接口**：加减币一律由各玩法接口在自己的业务语义里调 `apply`，
  避免出现「可以凭空加币」的通用端点。后台手动发/扣走 `POST /admin/players/:id/wallet/grant`（`wallet:write` 权限 + bizId 幂等 + `@Audit` 审计，**已实现**）。

# 十二、激励广告 / 加速（★线上变现）

## 12.1 原则

自愿看、看了有好处、绝不强制、不打断核心操作。

## 12.2 钩子

| 钩子 | 触发点 | 落点 |
| --- | --- | --- |
| 奖励翻倍 | 赛跑结算、任务领奖 | `/race/reward/double`、`/daily/task/claim` 带 `adToken` |
| 离线收益翻倍 | 领离线产出 | `/pet/offline/claim` 带 `adToken` |
| 免费加速 | 缩短冷却/成长 | `POST /boost/speedup` |
| 复活续命 | 赛跑失败 | `/race/revive` |
| 体力恢复 | 体力耗尽 | `POST /stamina/recover` |

## 12.3 校验（弱校验 + 强风控 · 软失败不死亡）

> 微信小游戏拿不到可靠的服务端广告回执，安全性来自**一次性 nonce + 频控 + 幂等 + 风控**，而非广告平台背书。

```
① 触发前：客户端调 /ad/token 领取一次性 nonce（服务端签发，绑 userId+scene，TTL 300s 存 Redis，每 scene 每日限 10 次）
② 播广告 → 客户端拿 nonce 作为 adToken 调对应增值接口（body 带 adToken + bizId）
③ 服务端：Lua 原子「读+校验 scene+删」核销 nonce（一次性）→ 业务态去重 → 幂等发奖（economy 用稳定 bizId）
④ nonce 失效/场景不符/超限 → 400 明确报错，不发奖；业务态标记（如 reward_doubled）兜住并发重复领
```

> **落地口径（与原设计稿的差异，以此为准）**：签发凭证的是**独立端点 `POST /ad/token`**，不是 `/ad/verify`。
> `/ad/verify` 是另一件事——「看广告直接领币」，自带每日次数上限与 bizId 幂等，不签发也不需要凭证。
> 两者互不依赖：`/ad/verify` 走「广告→发币」，`/ad/token` 走「广告→换增值行为」。
>
> 局限性要清楚：微信激励视频**没有标准服务端回调票据**，nonce 只能防「同一次广告重复兑换」和「凭空裸调增值接口」，
> 挡不住刻意刷量（客户端可以不看广告就领 nonce）。接入第三方 SSP 回调后，应在 `AdTokenService.issue` 处校验回调签名再签发。

## 12.4 接口

| 接口 | 方法 | 入参 | 返回 | 现状 |
| --- | --- | --- | --- | --- |
| `POST /ad/token` | POST | `{ scene }`（`race_double` \| `race_revive`） | `{ nonce, scene, expiresInSec, remaining }` | ✅ 已实现（一次性凭证签发，每 scene 每日限次） |

## 17.2 与后端对接铁律（前端直接用后端字段，不映射）

1. **Base URL** 指向 NestJS（开发 `http://<devbox>:8080`，生产走同域/网关）。
2. **鉴权**：管理员登录拿 JWT → axios 请求拦截器注入 `Authorization: Bearer <jwt>`；收到 401 跳登录。
3. **字段**：直接消费后端 JSON 出参字段名（**camelCase**，如 `hunger / lastSeenAt / gameCoin`）；id 按 **string**（bigint）处理；时间按 ISO8601(UTC) 字符串。
4. **响应**：成功是**资源 JSON**（无 `{ code:0, data }` 封套）；失败是 `{ code, message }`（`code` = HTTP 状态码）→ 在 axios 响应拦截器里统一弹 `message`。
5. **分页/筛选**：ProTable 的 `request` 适配后端分页出参形状（**以后端定的为准，前端适配**）。
6. **幂等**：后台写操作（发币/补偿/改状态）同样带 `body.bizId`。
