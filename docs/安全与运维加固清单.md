## A · 全项目没有任何限流与防爆破（上线阻塞）

### A.1 现状（已核准）

全仓库搜不到任何限流实现：

```bash
# 均无匹配
Grep "Throttler|ThrottlerModule|rate.?limit"  → No files with matches
Grep "failedAttempts|lockout"                  → No matches
```

`package.json` 未装 `@nestjs/throttler`；`src/main.ts` 全文 34 行，只有 `ValidationPipe`、
`AllExceptionsFilter`、CORS 三件事，没有任何限流中间件。

**两个登录端点都是裸奔的**：

| 端点                                                      | 已有防护                                                                                           | 缺失                                                    |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `POST /admin/auth/login`（`admin-auth.controller.ts:16`） | 口令 scrypt 散列；用户名不存在与口令错误**返回同一提示**（防账号枚举，`admin-auth.service.ts:41`） | 失败计数、账号锁定、IP 节流 **全部没有**                |
| `POST /auth/login`（`auth.controller.ts:9`）              | 依赖微信 code2session（code 一次性、有效期短）                                                     | 无节流；`WECHAT_MOCK_LOGIN=true` 时假登录路径同样无节流 |

`admin_user` 表的列是 `id, username, password_hash, display_name, status, last_login_at,
created_at, updated_at` —— **没有任何失败计数或锁定字段**。

### A.2 为什么这是上线阻塞级

后台超管的权限集合包含 `promo:write`（凭空签发营销积分）、`wallet:write`（直接改余额）、
`config:write`（热改全部玩法数值）。**攻破一个后台账号等于攻破整个经济系统**，
而现在拦在前面的只有一个口令 —— 没有次数限制，可以按字典无限次试到成功。

scrypt 散列保护的是「库被拖走之后」，它**完全不保护在线爆破**：
攻击者不需要看到散列，只要能无限次提交猜测。

反过来看这套代码在别处的防护标准，会发现这里的落差有多刺眼：

- 兑换码核销有每日失败次数上限（`promo.guard.dailyFailLimit`），
  且刻意让「码不存在」和「码已失效」返回同样含糊的提示，理由写在注释里：
  「区分开就等于给爆破者一个探测器」
- 广告凭证有一次性 nonce + 每场景每日限次
- 宠物互动有 Redis 冷却键 + 每日上限

**兑换码这种签发几百积分的入口都做了频控，能改全站配置的后台登录反而没做** ——
这不是漏了一个功能，是防护标准在最关键的地方断了档。

### A.3 改法

分两层，**两层都要**，因为它们防的不是同一件事。

#### 第一层：登录失败锁定（针对「猜某个账号的口令」）

不引新依赖，直接用已有的 `REDIS_CLIENT`，**照抄 `PromoService` 已经验证过的频控写法**
（`src/promo/promo.service.ts:203-230` 的 `assertUnderLimit` / `bumpCounter` / `readCounter`）：

```
键：login:fail:admin:{username}      滑动窗口 15 分钟，上限 5 次 → 锁定
键：login:fail:ip:{ip}               滑动窗口 15 分钟，上限 20 次 → 拒绝
```

四个必须照抄的设计点，不是可选项：

1. **成功登录清零计数**，否则一个手滑输错三次的运营会被自己的历史失败慢慢锁死。
2. **锁定期内即使口令正确也拒绝**，且**返回与口令错误相同的提示**。若锁定时给出
   「账号已锁定」这种区别对待，攻击者就能用它反推「刚才那次猜的口令是对的」。
3. **按 username + IP 双键**。只按 username，攻击者换着账号名撞库不受限；
   只按 IP，用代理池就绕过了。两个都记，任一超限即拒。
4. **软失败要选对方向**。这里和 `PromoService` 相反：兑换码的频控读失败按 0 处理
   （放行，不让加固项拖垮主功能），但**登录的频控读失败必须拒绝**——
   Redis 挂掉时放行登录，等于给攻击者一个「先打挂 Redis 再爆破」的路径。
   这个方向差异必须写进注释，否则后人「统一风格」时会把它改反。

#### 第二层：全局粗粒度限流（针对「打爆整个服务」）

装 `@nestjs/throttler@6.5.0`（对应 NestJS 11），在 `AppModule` 注册全局守卫，
给写接口一个宽松的兜底上限（如每 IP 每分钟 100 次），登录端点单独收紧。

⚠ **存储后端要想清楚**：`ecosystem.config.js:34-35` 当前是 `exec_mode: 'cluster'` +
`instances: 1`，单 worker，所以默认的内存存储此刻是准确的。但一旦把 `instances` 调大，
内存存储会变成**每个 worker 各算一份**，实际放行量翻 worker 倍数而没人会注意到。

两个选择：

| 方案                                                                                 | 代价                     | 建议                                           |
| ------------------------------------------------------------------------------------ | ------------------------ | ---------------------------------------------- |
| 默认内存存储 + 在 `ecosystem.config.js` 旁写死注释「调 instances 前先换 Redis 存储」 | 零依赖，但依赖后人读注释 | 短期可接受                                     |
| 引 `@nest-lab/throttler-storage-redis@1.2.0`                                         | 多一个社区依赖           | 更稳，且与项目「计数都放 Redis」的既有风格一致 |

第一层的登录锁定**本来就走 Redis**，天然跨 worker 正确，不受此影响。

### A.4 验收

- 单测：锁定阈值、成功后清零、锁定期口令正确仍拒、Redis 故障时**拒绝**（不是放行）
- e2e：连续 5 次错口令后第 6 次被拒；换正确口令仍被拒；等窗口过期后可登录
- 手工：`for i in $(seq 1 10)` 打 `/admin/auth/login`，确认第 6 次起被拦且提示不变

### A.5 落地（2026-08-27）

**第一层** `src/admin/auth/login-throttle.service.ts`，A.3 的四个设计点全部照做。
配套 8 条单测（`login-throttle.service.spec.ts`）与 3 条 e2e（`test/admin.e2e-spec.ts`）。

**与 A.3 的一处刻意偏离**：A.3 写的是「窗口内每失败一次就续期，因此攻击者持续尝试会
一直保持锁定」。实现改成了**锁定后不再计数、TTL 不续期**，15 分钟自动解锁。原因是
持续续期会让任何人拿着一个已知管理员用户名不停打就能把该账号永久锁死——防爆破变成了
拒绝服务。代价是攻击者每 15 分钟能试 5 次（约 480 次/天），对随机长口令毫无威胁。
理由已写进 `WINDOW_SEC` 上方的注释，避免后人当成 bug「修回去」。

**第二层** 装 `@nestjs/throttler@6.5.0` + `@nest-lab/throttler-storage-redis@1.2.0`
（即 A.3 表格里推荐的那一行，选它是为了 `instances` 调大时不会悄悄失效），
在 `AppModule` 注册 `APP_GUARD`。登录端点另挂 `@Throttle({ limit: 10, ttl: 60s })`，
限额写死、不随运维放宽 `THROTTLE_LIMIT` 一起变松。

⚠ **额度口径要注意**：`@nestjs/throttler` 把 handler 名一起哈希进计数键，
所以 `THROTTLE_LIMIT=100` 是「每 IP **每端点** 每分钟 100 次」而不是全站合计。
调参时别按总 QPS 估算。

**新增 `TRUST_PROXY_HOPS`（默认 1）**。这一项不能省：不设 trust proxy 时
Sealos ingress 后面所有请求的 `req.ip` 都是 ingress 那一个地址，
IP 维度的 20 次上限会把全部管理员一起锁在门外。

默认值 1 **已在公网链路上实测确认**（不是推断）：经
`https://ocqeeuitbygc.sealosbja.site` 打一次失败登录，服务端落到 Redis 的键是
`login:fail:ip:101.126.5.123`，与客户端真实出口 IP 逐字相同，
说明 Istio 网关恰好加一跳 `X-Forwarded-For`、Express 取到的是真客户端。
将来若在 DevBox 前面再叠一层网关（CDN、WAF 等），这个值要跟着加，
复现方法就是上面这一步：打一次失败登录，看 `login:fail:ip:*` 落的是谁。

真机实测（`127.0.0.1:8080`）：

```
第 1~6 次错口令        -> 401 {"code":401,"message":"用户名或密码错误"}
锁定期内用正确口令      -> 401 {"code":401,"message":"用户名或密码错误"}   # 逐字相同
第 11 次起（同一分钟）  -> 429
Redis: login:fail:admin:<user> = 5 (ttl 887s)，login:fail:ip:127.0.0.1 = 5
```

## B · 没有安全响应头（上线阻塞）

### B.1 现状（已核准）

`src/main.ts` 全文只有 CORS 一项安全配置（且逻辑是正确的：配了
`ADMIN_CORS_ORIGINS` 走白名单，否则仅非生产放开）。**未装 `helmet`**，因此缺：

`Content-Security-Policy`、`Strict-Transport-Security`、`X-Content-Type-Options`、
`X-Frame-Options` / `frame-ancestors`、`Referrer-Policy`。

### B.2 为什么要改

这不是「加个通用中间件」的例行公事，而是本项目的部署形态特别需要它：

后台控制台不是独立站点，而是由 NestJS `ServeStaticModule` 挂在**同端口同源**的
`/console`（见规格 §17.5）。这意味着：

- 一个带完整管理权限登录态的 HTML 界面，和全部 API 共享同一个源
- 缺 `X-Frame-Options` / `frame-ancestors` → `/console` 可被任意站点 iframe 嵌套，
  点击劫持能直接借用管理员的登录态触发发币、改配置这类操作
- 缺 `Content-Security-Policy` → 后台页面上任何一处 XSS 都能直取管理员令牌

而后台恰恰是权限最高的地方（见 A.2）。API 侧的响应头缺失危害有限（JSON 不执行），
**真正暴露的是那个管理界面**。

### B.3 改法

装 `helmet@8.3.0`，在 `main.ts` 的 `app.listen` 之前 `app.use(helmet(...))`。

⚠ **CSP 必须实测再定，不能照抄默认值**：Ant Design Pro / Umi 产物会用到内联样式
（antd 的 CSS-in-JS 运行时注入），helmet 的默认 CSP 会把它们拦掉，
表现是**后台页面样式全丢但控制台只有几条 CSP 报错**，很容易被误判成构建问题。
落地顺序应是：先只开非 CSP 的那几个头 → 再单独调 CSP 并在浏览器里逐条验证 `/console`
能正常渲染和登录，确认后才固化。

`ServeStaticModule` 的静态资源与 API 可以用同一套头，无需分流。

### B.4 验收

- `curl -I localhost:8080/health` 与 `curl -I localhost:8080/console/` 均返回预期头
- 浏览器实开 `/console`：登录、玩家管理、配置中心、兑换码四个页面渲染与交互正常，
  控制台**无 CSP 违规报错**（这一步不能省，CSP 配错的表现就是「看起来像别的 bug」）

### B.5 落地（2026-08-27）· **CSP 仍待浏览器验证**

装 `helmet@8.3.0`，策略集中在 `src/common/security/helmet.options.ts`。
非 CSP 的头已**直接强制**，`/health` 与 `/console/` 两处均已 curl 核对：

```
X-Frame-Options: DENY                 Strict-Transport-Security: max-age=31536000; includeSubDomains
X-Content-Type-Options: nosniff       Referrer-Policy: no-referrer
Cross-Origin-Opener-Policy: same-origin   Cross-Origin-Resource-Policy: same-origin
X-DNS-Prefetch-Control: off           X-Permitted-Cross-Domain-Policies: none
```

CSP 按 B.3 要求的顺序分档落地，用 `CSP_MODE` 控制（`enforce` / `report-only` / `off`），
**当前默认 `report-only`**。原因是本机既无浏览器 MCP 也无 Chromium，
B.4 里那条「浏览器实开 /console 逐页确认无 violation」我无法执行；
而 CSP 配错的表现正是「样式全丢/白屏但只有几条控制台报错」，
未经浏览器验证就 enforce，等于拿后台可用性赌一把。

已能静态确认的两点（降低但不消除风险）：

- `admin-web/dist/index.html` **无任何内联 `<script>`/`<style>`**，打包产物也不含
  `eval`/`new Function`（`grep -c "eval(" dist/*.js` 全为 0）。因此
  `script-src` 没给 `'unsafe-inline'`，这是这条 CSP 最值钱的部分。
- `style-src` 必须给 `'unsafe-inline'`：antd 的 `@ant-design/cssinjs` 在运行时往
  `<head>` 注入 `<style>`，nonce/hash 覆盖不到动态注入。

**遗留动作（需人工）**：浏览器打开 `/console`，走一遍登录 / 玩家管理 / 配置中心 /
兑换码，确认 DevTools Console 无 `Content-Security-Policy` 报错，然后把 `.env` 的
`CSP_MODE` 改成 `enforce` 并重启。**在此之前 CSP 不提供任何实际防护**
（挡点击劫持的是上面那个 `X-Frame-Options: DENY`，它已经生效）。

## C · admin-web 的 lint 卡口实际失效

### C.1 现状（已核准）

`pnpm lint`（`biome check .`）报 **241 errors / 88 warnings**，是个永久红灯。
红灯久了等于没灯 —— 没人会在 241 条既有报错里分辨自己新引入的那一条。

而后端那侧是**双闸强制 0 问题**（husky `pre-commit` + `prebuild` 的 `lint:check
--max-warnings 0`）。两边标准差了一整个数量级。

更要紧的是**卡口范围**：`package.json:37-41` 的 lint-staged 只配了

```json
"{src,test}/**/*.ts": ["eslint --max-warnings 0"]
```

`admin-web/` **完全不在提交前卡口内**。也就是说后端一个 warning 都进不去，
前端可以随便提交任何东西。

### C.2 根因（不是「代码写得差」）

拆开这 241 条会发现绝大部分根本不是代码问题：

**根因一：把生成产物当源码在 lint。** `admin-web/biome.json` 的
`files.includes` 是 `["src/**/*.ts", "src/**/*.tsx", ".umirc.ts"]`，
把 Umi 生成的 `src/.umi-production/`（**43 个生成文件**）整个扫进来了。
手写代码只有 32 个文件。

只对手写代码跑：**80 errors / 2 warnings**，其余全来自生成目录。

**根因二：格式规则与代码风格不一致。** `biome.json` 没配
`javascript.formatter.quoteStyle`，biome 默认双引号，而整个代码库用单引号。
于是每个文件都报 format 错。

**根因三：a11y 规则与 Ant Design Pro 的惯用写法冲突。**
`useValidAnchor` / `useKeyWithClickEvents` / `noStaticElementInteractions` 三条，
撞的是 ProTable option 列里 `<a onClick={...}>操作</a>` 这个 Pro 官方范式，
现有页面（Config/Items、Config/Kv、Economy/Exchange…）全都在用。

### C.3 改法（已在副本上实测通过）

三步，**顺序不能换**（不先修配置就直接 `--write`，会把生成目录一起重排）：

1. **`biome.json` 排除生成目录**：`files.includes` 加 `"!src/.umi/**"`、
   `"!src/.umi-production/**"`（注意 biome 2.x 会提示 `useBiomeIgnoreFolder`，
   按它的建议写成忽略文件夹的形式更规范）。
2. **对齐风格**：加 `"javascript": { "formatter": { "quoteStyle": "single",
"jsxQuoteStyle": "double" } }`；把上述三条 a11y 规则关掉，
   并在 `biome.json` 旁注明「关掉是因为撞 Pro 的 option 列范式，
   不是不在乎无障碍」——否则后人不知道能不能打开。
3. **一次性 `biome check --write`** 让格式归位。

**实测结果**（在 `/tmp` 副本上跑，未动真实文件）：
`Checked 34 files, Fixed 20 files` → 复查 **0 errors**，仅剩 2 warnings
（`Role/index.tsx:32,72` 的 `noNonNullAssertion`，可单独修）。
抽查 diff 规模：`access.ts` 6 行、`types.ts` 7 行、`wallet.ts` 7 行 —— 纯机械重排。

4. **最后把 admin-web 纳入 lint-staged**，让前端也进提交前卡口：

```json
"admin-web/**/*.{ts,tsx}": ["biome check --no-errors-on-unmatched"]
```

⚠ **本仓库不是 git 仓库**（无 `.git`），`--write` 改错了没有 `git checkout` 可退。
执行前先 `cp -r admin-web/src /tmp/admin-web-src.bak`。

### C.4 验收

- `cd admin-web && pnpm lint` → 0 errors
- `pnpm build` 仍通过（格式重排不该影响构建，但必须实测）
- 浏览器实开 `/console` 抽查两三个页面，确认重排没改变行为
- 故意在 admin-web 里写一处报错并尝试提交，确认被 pre-commit 拦住

### C.5 落地

配置改法与 C.3 一致，但**格式化的活交给了 Prettier 而不是 biome**：后端本来就用
Prettier，让两边共用一套格式化器比让 biome 去模仿 Prettier 的风格更省事。
于是 `biome.jsonc` 只当 linter（`formatter.enabled: false`），
`admin-web` 自带 `.prettierignore` 管生成目录。

lint-staged 的范围也一并对齐成与 `lint:check` / `verify:web` 相同的四处
（`src`、`test`、`scripts/dev`、`admin-web`）——三者范围不一致就等于「本地过了、全量挂了」。
`admin-web` 那条跑的是整个子项目而非暂存文件：biome 与 Prettier 要以 `admin-web`
为 cwd 才找得到自己的配置，逐文件传参反而读不到规则。实测耗时约 1.1s。

**C.4 里「浏览器抽查」那条仍未做**（无浏览器环境），但补了更耐久的东西：
`admin-web` 接入 vitest，给 `src/utils/menu-tree.ts` 写了 12 条单测。
挑这个文件是因为菜单真相源统一到数据库时，在它身上抓出过两个真实缺陷
（权限不足时残留点开是空的目录；catalog 按前缀放行导致 `/system/*` 整个子树越权），
而当时只靠一次性脚本验证、脚本已删。这 12 条用例做过变异测试：
把上述两个缺陷分别改回去，以及去掉剪枝、把叶子改成只认全等，四种改法都会让对应用例变红。

> vitest 需要 vite ≥6，而 Umi 树里是 vite 4.5.2，故给 `admin-web` 显式加了
> `vite@^7` 的 devDependency。Umi 走 webpack（`.umirc.ts` 未启用 vite），
> 加完后 `pnpm build` 产物哈希与加之前完全一致，确认无渗入。

## D · 运维：日志无轮转 + .env 键缺失

### D.1 PM2 日志无轮转（已核准）

`pm2 list` 无 `pm2-logrotate` 模块。当前 `logs/` 总计 668K，其中
`warmpet-api-out.log` 已 **646KB 且只增不减**。

跑在磁盘有限的 Sealos DevBox 上，这是个「几个月后突然写不进日志」的定时炸弹。
更糟的失败形态是：**磁盘满会先打挂 PostgreSQL 或 Redis 的写入**，
排查时看到的现象是数据库报错，与真实原因（日志占满盘）隔了一层。

改法：`pm2 install pm2-logrotate`，配 `max_size` / `retain` / `compress`,
并把配置写进 `ecosystem.config.js` 旁的注释或部署脚本，
否则重建 DevBox 后这一步会被忘掉（PM2 模块不在 `ecosystem.config.js` 里）。

### D.2 `.env` 缺 6 个已文档化的键（已核准）

`.env.example` 有、`.env` 没有：`DB_POOL_MAX`、`DB_POOL_MIN`、`DB_POOL_IDLE_MS`、
`DB_POOL_ACQUIRE_MS`、`DB_KEEPALIVE`、`DB_KEEPALIVE_DELAY_MS`。

**无功能影响**（走代码默认值），方向也是安全的那一边（示例比实际多，
不是「实际用了未文档化的密钥」）。但连接池大小是那种「压测时才想调、
而那时你希望它已经是显式的」的参数，建议显式补上并写清当前取值的理由。

### D.3 验收

- `pm2 conf pm2-logrotate` 显示预期配置；手工灌一批日志确认切割与压缩生效
- 重启后 `.env` 的池参数在启动日志或 `/health` 扩展信息里可见（或至少有注释说明）

### D.4 落地（2026-08-27）

**D.1 已修。** `pm2 install pm2-logrotate`，配置为
`max_size=10M` / `retain=14` / `compress=true` / `rotateInterval='0 0 * * *'` /
`rotateModule=true`，并 `pm2 save`。

PM2 模块装在守护进程上（`~/.pm2`）而不在本仓库里，换机或重建 DevBox 后不会跟着回来，
所以**完整的重装命令已抄进 `ecosystem.config.js` 顶部注释**——这正是 D.1 提醒过的坑。

**D.2 复核后判定为误报，不改。** `.env.example` 第 20 行本来就写着
「连接池 / keepAlive（均可选，留空走代码默认值）」，且示例里的 6 个取值与
`env.validation.ts` 的 Joi 默认值逐个相同。`.env` 不设它们**正是文档描述的预期行为**，
不是「缺键」。若将来压测要调，直接在 `.env` 里写显式值即可，无需先补齐再改。
