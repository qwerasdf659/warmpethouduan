# warmpet-api 账本与交易系统架构设计

> 生成时间：2026-08-26
> 基准：本仓库实际代码（NestJS 11 / TypeORM 1.1 / PostgreSQL 16 / Redis 7 / PM2）
> 前提：**项目未上线**，允许破坏性重构，不保留旧接口与旧表，无数据迁移负担
> 目标：支持玩家间交易（3a~3d 全部），同时把长期维护成本压到最低
>
> **落地状态：期 1~5 已全部实现并验证（2026-08-27）。** 实现与本文的差异、
> 以及本文若干处需要修正的表述，见文末 [§12 落地记录](#12-落地记录2026-08-27)。

## 0. 决策摘要

| 决策         | 结论                                                     | 理由                                                      |
| ------------ | -------------------------------------------------------- | --------------------------------------------------------- |
| 账本模式     | **混合式**：发行/销毁单边分录，转移多边分录且凭证内平衡  | 见 §2.2，避免单行热点又不放弃交易场景的强校验             |
| 是否复式记账 | **不做**完整会计复式（无科目表、无借贷方向、无期末结转） | 无对手方结算、无提现、无监管报表要求                      |
| 资产建模     | 行式统一账本（货币 + 可堆叠道具 + 唯一实例）             | 加币种零 DDL；消灭现有「货币有账本、道具没账本」的双标准  |
| 幂等         | **收敛到一处**：`asset_txn.biz_id` 全局唯一              | 替代现在分散在 4 张表的唯一索引                           |
| 并发控制     | 保留条件原子 UPDATE，**不引入** `SELECT FOR UPDATE`      | 现有写法更优，见 §5.3                                     |
| 分布式事务   | **不引入** Seata/TCC/Saga                                | 单库单服务，本地事务即最强一致                            |
| 合规红线     | 落成 DB CHECK 约束，不靠文档和人                         | 见 §3                                                     |
| 交易分档     | 架构一次按 3d 设计，功能分 5 期上线                      | 3d 的模型包含 3a/3b/3c 所需的一切                         |
| 过期能力     | **全部货币支持批次（lot）+ FIFO**，是否启用逐资产配置    | 批次归属无法事后补；按到期日归并使「不启用」成本归零      |
| 唯一物品     | **皮肤/配饰实例化 + 支持限量编号**                       | 交易要求物品身份；限量编号产生收藏溢价，超发由 CHECK 兜住 |
| 扭蛋产出     | **不再产出 `game_coin`**，只产出道具与消耗品             | 解除「交易媒介 ↔ 开箱产物」冲突                           |

## 1. 现状与缺口

### 1.1 现状（已经做对的部分，重构中必须保留）

- `EconomyService.apply` 是唯一记账入口，业务代码不得直接改余额
- 余额变更与流水写入在同一 DB 事务内
- 余额变更用单语句 `UPDATE wallet SET col = col + $delta WHERE col + $delta >= 0`，**无锁、无竞态**，余额不足表现为影响 0 行
- 幂等以 `uq_ledger_user_biz_pool` 唯一索引为持久权威，Redis 只做 24h 请求级去重
- `ledger` 只追加不可改，带 `balance_after` 供逐笔回溯
- `ReconcileService` 每日 04:10 校验 `wallet == SUM(ledger.delta)`
- 双池物理隔离，接口层禁止互转

### 1.2 缺口（本次重构要解决的）

| #   | 缺口                                       | 影响                                                                                         |
| --- | ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| G1  | 道具（`item_owned.qty`）无流水、无持久幂等 | 玩家投诉「我的皮肤没了」查不出来；后台补发只靠 Redis 24h 去重                                |
| G2  | `apply` 一次只能动一个池                   | 扭蛋「扣币 + 发多个奖品」非原子，中间失败会扣钱不给东西                                      |
| G3  | 无发行/回收口径                            | 无法回答「本月发了多少币」「`marketing_point` 待兑付负债多少」                               |
| G4  | 无实例模型                                 | 装扮不可交易（交易需要物品身份，`qty` 表达不了「这一件」）                                   |
| G5  | 无冻结（frozen）                           | 挂单/竞价无法锁定资产                                                                        |
| G6  | 幂等键分散在 4 张表                        | `ledger` / `redeem_order` / `gacha_draw` / `promo_redemption` 各一套，新增业务容易漏         |
| G7  | `item_def.type` 混了三种语义               | `qty` 对皮肤恒为 1（无意义）、对家具是件数、对消耗品是余量，每个读它的地方都要知道该怎么解释 |
| G8  | `ledger` 无分区无归档策略                  | 长期无界增长                                                                                 |

## 2. 设计原则

### 2.1 不变量（对账作业逐条校验，见 §7）

1. 每张 `kind='transfer'` 的凭证，按资产分组的 `SUM(delta)` 必须为 0
2. `asset_balance.available + frozen == SUM(asset_entry.delta)`（按 account × asset）
3. `asset_balance.frozen == SUM(asset_entry.frozen_delta)`
4. 玩家账户 `available >= 0 AND frozen >= 0`（DB CHECK 兜底）
5. 每个 `item_instance` 的 `SUM(item_instance_entry.delta) == 1`（存在且仅属一人）
6. `item_instance.owner_account_id` 等于最后一条 `delta=+1` 分录的账户
7. `ESCROW` 账户持有的实例数 == `state='escrowed'` 的实例数
8. `asset_def` 中不存在 `tradable AND redeemable` 或 `tradable AND gacha_output` 的行
9. `SUM(asset_lot.remaining) == asset_balance.available` 且 `SUM(asset_lot.frozen) == asset_balance.frozen`（按 account × asset）
10. 不存在 `expires_at < now() AND remaining > 0` 的批次（过期作业无遗漏）
11. `asset_def.minted_count <= mint_limit`（限量未超发，DB CHECK 兜底）

### 2.2 关键架构判断：为什么是混合式，而不是全双录

**问题**：如果所有变动都要求有对手方（发行方 `MINT`、销毁方 `BURN`），那么每个玩家的每次互动产币都要 UPDATE `MINT` 账户的同一行 `asset_balance` —— **单行热点**，全服写入被串行化在一行上。这是全双录方案在游戏场景下的致命伤。

**方案**：按凭证类型区分校验强度。

| 凭证 kind  | 分录数   | 是否要求平衡                      | 场景                                          |
| ---------- | -------- | --------------------------------- | --------------------------------------------- |
| `issue`    | 1        | 否                                | 互动/离线/签到/赛跑/图鉴/广告/后台发放/兑换码 |
| `burn`     | 1        | 否                                | 购买/加速/兑换扣费/扭蛋抽费/后台扣减          |
| `transfer` | ≥2       | **是**（按资产求和为 0）          | 玩家间赠送、寄售成交、竞价、手续费            |
| `freeze`   | ≥1       | 是（`delta + frozen_delta` 守恒） | 挂单锁物品、出价锁币                          |
| `reversal` | 同原凭证 | 同原凭证                          | 冲正                                          |

发行和销毁本来就是凭空产生和消失（运营想发就发、积分会过期），**守恒在这里不成立，不该假装它成立**。它们的口径由 §7 的发行日报承担。

**这不是天工那种「半双录」。** 区别在于：天工给转移场景写了个对手方分录但 `balance_before/after` 填 0（对手方余额是假的，守恒只能靠全局启发式）；本设计是明确区分两类凭证，`transfer` 做真双录且系统账户持有真实余额，`issue`/`burn` 不假装有对手方。校验能定位到具体哪张凭证坏了，而不是只知道「某处有问题」。

**因此系统账户只有两个**：`FEE`（手续费归集）和 `ESCROW`（挂单托管）。没有 `MINT`/`BURN`。这两个账户的写入频率等于交易频率，远低于玩法产出频率，热点可接受；真热了再按 `id % N` 分片。

## 3. 合规边界（决定架构开关，不是免责声明）

### 3.1 判断标准：资金闭环的三环

变现闭环需要三个环节，**断掉任意一环即安全**：

| 环                 | 现状                               | 全开交易后                               |
| ------------------ | ---------------------------------- | ---------------------------------------- |
| 入口（钱进来）     | 无（不能充值买币）                 | 无 —— **但玩家可自建**：站外微信私下转账 |
| 流转（玩家间转移） | 无                                 | 有                                       |
| 出口（换回价值）   | **有**（`marketing_point` 兑实物） | 有                                       |

结论：**「平台不提供提现」不构成保护**。执法认定的依据是「是否存在事实上的变现通路」，而非「平台是否提供提现功能」。一旦有交易市场，站外币商收购是必然而非可能。

参考口径：文市发〔2016〕32 号第（九）（十）条 —— 虚拟货币不得兑换法定货币或实物；虚拟道具不得兑换法定货币，兑换「小额实物」留有口子。该通知已失效但无新法替代，仍是实践参考。另《关于加强网络游戏虚拟货币管理工作通知》第（二十）条禁止「在用户直接投入现金或虚拟货币的前提下，采取抽签、押宝、随机抽取等偶然方式分配游戏道具」。已有兑换话费卡被判开设赌场罪的判例（2021 湘 0923 刑初 189 号）。

微信平台侧：小游戏运营规范要求虚拟商品购买必须走小程序虚拟支付，明确不鼓励玩家间私下交易，严禁销售未备案的游戏货币。

> 以上为技术调研结论，非法律意见。最终定性需法务确认。本文的作用是**把确定的红线固化到数据库层**，使其不依赖任何人记得住。

### 3.2 红线的固化方式

```sql
CONSTRAINT ck_asset_no_trade_redeem CHECK (NOT (tradable AND redeemable))
CONSTRAINT ck_asset_no_trade_gacha  CHECK (NOT (tradable AND gacha_output))
```

放开这两条约束需要**显式迁移 + 在本文 §10 追加一条决策记录**，不能顺手改配置。

### 3.3 资产的可交易性分配

| 资产               | kind      | tradable | redeemable | gacha_output     | 说明                                               |
| ------------------ | --------- | -------- | ---------- | ---------------- | -------------------------------------------------- |
| `game_coin`        | currency  | ✅       | ❌         | ❌（已拍板移除） | 交易媒介。原扭蛋产币能力移除，见下方 D1 结论       |
| `marketing_point`  | currency  | ❌       | ✅         | ❌               | 可兑实物 ⇒ 禁止流转                                |
| 皮肤 / 配饰        | unique    | ✅       | ❌         | ❌               | 交易标的，实例模型                                 |
| 家具               | stackable | ✅       | ❌         | ❌               | 交易标的，数量模型                                 |
| 消耗品             | stackable | ✅       | ❌         | ❌               |                                                    |
| 扭蛋产出的限定道具 | unique    | ❌       | ❌         | ✅               | 「投入→随机→可变现」是开箱模式，敏感度高于交易本身 |
| 兑换中心实物       | —         | —        | —          | —                | 非游戏内资产，走 `redeem_order`，不入账本          |

**D1 已拍板：扭蛋不再产出 `game_coin`，只产出道具与消耗品。**

原冲突：`game_coin` 既是交易媒介（必须 `tradable`）又是扭蛋产出，两个标记同时为真会被 `ck_asset_no_trade_gacha` 拦住。落地改动：

1. `gacha` 奖池配置移除 `game_coin` 奖项，改为道具 / 消耗品 / 限定收藏品
2. `game_coin.gacha_output = false`
3. `LEDGER_REASONS` 中 `gacha` 仅用于抽奖扣费（货币出），产出侧统一走 `RewardService.grant`
4. 扭蛋产出的限定道具保持 `tradable = false`（避免「投入→随机→可变现」链路）

## 4. 数据模型

### 4.1 账户

```sql
CREATE TABLE account (
  id          BIGSERIAL   PRIMARY KEY,
  kind        varchar(8)  NOT NULL,
  user_id     bigint      NULL REFERENCES "user"(id),
  system_code varchar(32) NULL,          -- 'FEE' | 'ESCROW'
  status      varchar(16) NOT NULL DEFAULT 'active',
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_account_kind CHECK (kind IN ('user','system')),
  CONSTRAINT ck_account_ref CHECK (
    (kind = 'user'   AND user_id IS NOT NULL AND system_code IS NULL) OR
    (kind = 'system' AND user_id IS NULL     AND system_code IS NOT NULL)
  )
);
CREATE UNIQUE INDEX uq_account_user   ON account(user_id)     WHERE user_id IS NOT NULL;
CREATE UNIQUE INDEX uq_account_system ON account(system_code) WHERE system_code IS NOT NULL;
```

`user_id` 外键为 `NO ACTION`：有资金流水的玩家不允许硬删，业务上应改用封禁。

### 4.2 资产定义

```sql
CREATE TABLE asset_def (
  code                 varchar(48) PRIMARY KEY,
  kind                 varchar(16) NOT NULL,   -- currency | stackable | unique
  name                 varchar(48) NOT NULL,
  tradable             boolean NOT NULL DEFAULT false,
  redeemable           boolean NOT NULL DEFAULT false,
  gacha_output         boolean NOT NULL DEFAULT false,
  trade_cooldown_hours int     NOT NULL DEFAULT 72,   -- 获得后多久可交易
  -- 过期：发行时按此计算批次到期日；NULL = 该资产永不过期
  expire_days          int     NULL,
  -- 限量：NULL = 不限量。minted_count 由发行时原子自增
  mint_limit           int     NULL,
  minted_count         int     NOT NULL DEFAULT 0,
  enabled              boolean NOT NULL DEFAULT true,
  sort_order           int     NOT NULL DEFAULT 0,
  meta                 jsonb   NOT NULL DEFAULT '{}',
  created_at           timestamptz NOT NULL DEFAULT now(),
  updated_at           timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_asset_kind CHECK (kind IN ('currency','stackable','unique')),
  CONSTRAINT ck_asset_no_trade_redeem CHECK (NOT (tradable AND redeemable)),
  CONSTRAINT ck_asset_no_trade_gacha  CHECK (NOT (tradable AND gacha_output)),
  CONSTRAINT ck_asset_expire_days CHECK (expire_days IS NULL OR expire_days > 0),
  -- 限量超发的结构性防线：任何路径都改不出 minted_count > mint_limit
  CONSTRAINT ck_asset_mint_limit  CHECK (mint_limit IS NULL OR minted_count <= mint_limit)
);
```

替代现有 `item_def`。`slot` / `comfort` / `grid_w` / `grid_h` 等表现层字段收进 `meta`，账本层只关心 kind、三个合规开关、过期与限量。

初始配置（D2/D3 拍板结果）：

| code              | expire_days          | mint_limit | 说明                                       |
| ----------------- | -------------------- | ---------- | ------------------------------------------ |
| `game_coin`       | `NULL`               | `NULL`     | 永不过期（符合玩家预期），但模型随时可开启 |
| `marketing_point` | 待运营定（建议 365） | `NULL`     | 可兑实物 ⇒ 负债必须封顶                    |
| 限定皮肤          | `NULL`               | 如 100     | 带 `serial` 编号，产生收藏溢价             |
| 普通皮肤 / 家具   | `NULL`               | `NULL`     |                                            |

**限量发行的原子分配**（限量物发行频率低，单行热点可接受）：

```sql
UPDATE asset_def
   SET minted_count = minted_count + 1, updated_at = now()
 WHERE code = $1 AND (mint_limit IS NULL OR minted_count < mint_limit)
RETURNING minted_count;   -- 即为本件的 serial；影响 0 行 = 已售罄
```

### 4.3 凭证头（幂等的唯一权威）

```sql
CREATE TABLE asset_txn (
  id          BIGSERIAL    PRIMARY KEY,
  biz_id      varchar(160) NOT NULL,
  kind        varchar(16)  NOT NULL,
  reason      varchar(32)  NOT NULL,
  ref_type    varchar(32)  NULL,
  ref_id      varchar(64)  NULL,
  reversal_of bigint       NULL REFERENCES asset_txn(id),
  created_at  timestamptz  NOT NULL DEFAULT now(),
  CONSTRAINT uq_asset_txn_biz_id UNIQUE (biz_id),
  CONSTRAINT ck_asset_txn_kind CHECK (kind IN ('issue','burn','transfer','freeze','reversal'))
);
CREATE INDEX idx_asset_txn_created ON asset_txn(created_at);
CREATE INDEX idx_asset_txn_reason  ON asset_txn(reason, created_at);
```

**幂等收敛到这一张表的 `biz_id`**，替代现有 4 张表的唯一索引。一次操作 N 条分录整体原子、整体幂等。

> ⚠ **`biz_id` 全局唯一 ⇒ 必须自带用户区分。** 现有 `ledger` 的幂等键是 `(user_id, biz_id, pool)`，带 `user_id` 是为了防不同玩家撞同一个客户端 UUID。提到凭证头后不再有 `user_id` 参与，因此 `LedgerService` 必须**强制在内部拼接** `bizId` 前缀，调用方无法绕过：
>
> ```
> 玩家发起：  u{userId}:{domain}:{action}:{clientBizId}
> 服务端派生：sys:{domain}:{action}:{key}
> 交易撮合：  mkt:{listingId}:{stage}
> ```
>
> `varchar(160)` 是为前缀留的余量。

### 4.4 分录（按月分区）

```sql
CREATE TABLE asset_entry (
  id            BIGSERIAL,
  txn_id        bigint      NOT NULL,
  account_id    bigint      NOT NULL,
  asset_code    varchar(48) NOT NULL,
  delta         bigint      NOT NULL DEFAULT 0,
  frozen_delta  bigint      NOT NULL DEFAULT 0,
  balance_after bigint      NOT NULL,
  frozen_after  bigint      NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (id, created_at),
  CONSTRAINT ck_entry_nonzero CHECK (delta <> 0 OR frozen_delta <> 0)
) PARTITION BY RANGE (created_at);

CREATE INDEX idx_entry_account ON asset_entry(account_id, asset_code, created_at DESC);
CREATE INDEX idx_entry_txn     ON asset_entry(txn_id);
```

设计说明：

- **分区表的 PK 与 UNIQUE 必须包含分区键**，这是 PG 的硬限制。分录上因此不设唯一约束 —— 不需要：幂等已经在 `asset_txn.biz_id`（非分区表，可全局唯一），凭证插入成功才写分录，同一事务内保证一一对应。这正是「幂等收敛到一处」带来的额外好处。
- TypeORM 1.1 不生成分区 DDL。**分区表用 raw SQL 迁移建**，实体只映射父表做只读查询（`find` / `findAndCount` 正常工作）。
- 分区维护：迁移里预建未来 12 个月分区，另加一个每月的 PM2 定时任务补建。不装 `pg_partman`（多一个扩展依赖，Sealos 托管 PG 未必允许）。
- **归档只允许 DETACH + 转储到对象存储，禁止 DELETE**。物理删除会摧毁回档能力（见 §8.6）。

### 4.5 余额

```sql
CREATE TABLE asset_balance (
  account_id bigint      NOT NULL REFERENCES account(id),
  asset_code varchar(48) NOT NULL REFERENCES asset_def(code),
  available  bigint      NOT NULL DEFAULT 0,
  frozen     bigint      NOT NULL DEFAULT 0,
  updated_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, asset_code),
  CONSTRAINT ck_balance_non_negative CHECK (available >= 0 AND frozen >= 0)
);
```

因为没有 `MINT` 账户，所有账户（含 `FEE`/`ESCROW`）都非负，CHECK 可以无例外地统一施加。

### 4.6 唯一物品实例

```sql
CREATE TABLE item_instance (
  id               BIGSERIAL   PRIMARY KEY,
  asset_code       varchar(48) NOT NULL REFERENCES asset_def(code),
  owner_account_id bigint      NOT NULL REFERENCES account(id),
  state            varchar(16) NOT NULL DEFAULT 'held',
  serial           int         NULL,               -- 限量编号
  acquired_at      timestamptz NOT NULL DEFAULT now(),
  tradable_after   timestamptz NULL,               -- 冷却期到期时间
  minted_txn_id    bigint      NOT NULL REFERENCES asset_txn(id),
  CONSTRAINT ck_instance_state CHECK (state IN ('held','listed','escrowed'))
);
CREATE INDEX idx_instance_owner ON item_instance(owner_account_id, asset_code);
CREATE UNIQUE INDEX uq_instance_serial ON item_instance(asset_code, serial) WHERE serial IS NOT NULL;

CREATE TABLE item_instance_entry (
  id          BIGSERIAL   PRIMARY KEY,
  txn_id      bigint      NOT NULL REFERENCES asset_txn(id),
  instance_id bigint      NOT NULL REFERENCES item_instance(id),
  account_id  bigint      NOT NULL REFERENCES account(id),
  delta       smallint    NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_instance_entry_delta CHECK (delta IN (-1, 1)),
  CONSTRAINT uq_instance_entry UNIQUE (instance_id, txn_id, account_id)
);
```

唯一物品走**真双录**（转移必须成对 ±1），所以「物品凭空产生」结构性不可能。`owner_account_id` 是从分录派生的缓存，由 §7 的对账校验漂移。

**这解决了 G7**：皮肤/配饰进 `item_instance`（有身份，可交易，`dex` 图鉴的天然数据源）；家具/消耗品进 `asset_balance`（数量语义）。不再有「`qty` 对某些 type 无意义」的约定。

**限量编号（已拍板启用）**：`serial` 由 §4.2 的原子分配语句产生，`uq_instance_serial` 保证同一 `asset_code` 下编号不重复，`ck_asset_mint_limit` 保证结构性不可超发。限量编号在奢侈品与潮玩行业是核心玩法 —— 编号本身产生收藏溢价（「第 7/100 件」），而这只有在实例化之后才可能，事后无法补（无法确定历史上谁先获得）。

`tradable_after = acquired_at + asset_def.trade_cooldown_hours`，在 `mint` 与 `transfer` 时统一写入，防盗号即刻套现。

### 4.9 批次（lot）与过期

**为什么必须现在建**：批次归属信息无法事后补。一旦上线跑几个月，玩家手上的余额是哪一批发的、该哪天过期，这个信息永久丢失，只能全部当作永不过期。

**关键设计：批次按到期日归并，而不是每次发行建一个批次。** 这让「不启用过期」的成本归零。

```sql
CREATE TABLE asset_lot (
  id            BIGSERIAL   PRIMARY KEY,
  account_id    bigint      NOT NULL REFERENCES account(id),
  asset_code    varchar(48) NOT NULL REFERENCES asset_def(code),
  remaining     bigint      NOT NULL DEFAULT 0,   -- 该批次剩余可用
  frozen        bigint      NOT NULL DEFAULT 0,   -- 该批次被冻结部分
  issued_total  bigint      NOT NULL DEFAULT 0,   -- 累计发行（只增，审计用）
  expires_at    timestamptz NULL,                 -- NULL = 永不过期
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_lot_non_negative CHECK (remaining >= 0 AND frozen >= 0),
  CONSTRAINT ck_lot_within_issued CHECK (remaining + frozen <= issued_total)
);

-- 归并键：PG15+ 的 NULLS NOT DISTINCT 让 expires_at IS NULL 也受唯一约束覆盖
CREATE UNIQUE INDEX uq_lot_bucket
  ON asset_lot(account_id, asset_code, expires_at) NULLS NOT DISTINCT;

-- FIFO 消耗索引：先扣最早到期的，永不过期的排最后
CREATE INDEX idx_lot_fifo ON asset_lot(account_id, asset_code, expires_at NULLS LAST, id)
  WHERE remaining > 0;

-- 过期作业扫描索引
CREATE INDEX idx_lot_expiring ON asset_lot(expires_at)
  WHERE expires_at IS NOT NULL AND remaining > 0;
```

**归并带来的规模效果**：

| 资产              | expire_days | 每玩家批次数       | 读写性能             |
| ----------------- | ----------- | ------------------ | -------------------- |
| `game_coin`       | `NULL`      | **恒为 1 行**      | 与现有 `wallet` 相同 |
| `marketing_point` | 365（按日） | ≤ 365 行，滚动淘汰 | FIFO 扫描 1~2 行     |
| 若改按月归并      | —           | ≤ 12 行/年         | 可忽略               |

> 到期日的归并粒度由 `expire_days` 与截断策略决定。建议 `marketing_point` 按**自然月末**截断（`date_trunc('month', now()) + interval '1 month' + expire_days`），使每玩家每月一行，而不是每天一行。

**发行（UPSERT 归并）**：

```sql
INSERT INTO asset_lot (account_id, asset_code, remaining, issued_total, expires_at)
VALUES ($1, $2, $3, $3, $4)
ON CONFLICT (account_id, asset_code, expires_at)
DO UPDATE SET remaining    = asset_lot.remaining    + EXCLUDED.remaining,
              issued_total = asset_lot.issued_total + EXCLUDED.issued_total,
              updated_at   = now()
RETURNING remaining;
```

**消耗（FIFO 跨批次）**：按 `expires_at NULLS LAST, id` 升序遍历，逐批扣减直到凑够数量；总量不足则整个事务回滚（`asset_balance` 的条件 UPDATE 会先一步拦住，FIFO 只负责分摊）。

> **已在本项目数据库实测通过**（PostgreSQL 16.4，2026-08-27）：
>
> - `CREATE UNIQUE INDEX ... NULLS NOT DISTINCT` 生效，重复 `NULL` 到期日被 `23505` 拦住
> - `ON CONFLICT (account_id, asset_code, expires_at) DO UPDATE` 在 `expires_at IS NULL` 时**能正确命中该索引**（这是归并设计的承重点：PG15 之前 `NULL` 互不相等会导致每次发行新建一行）
> - `game_coin` 连续三次发行（+100/+12/+8）归并为**单行** `remaining=120`；`marketing_point` 两个到期日正确分为两行
> - FIFO 排序 `expires_at NULLS LAST` 顺序正确

**三层真相与职责划分**：

| 层              | 角色                   | 用途                       |
| --------------- | ---------------------- | -------------------------- |
| `asset_entry`   | 追加流水，唯一审计真相 | 对账、回溯、发行日报       |
| `asset_lot`     | 余额的**分桶实现**     | FIFO 消耗、过期批处理      |
| `asset_balance` | lot 的**聚合缓存**     | 热路径读余额、条件原子扣减 |

**分录不细分到 lot。** 一次消耗可能横跨多个批次，但分录仍只记「该账户该资产净变动多少」。理由：玩家关心「我的币少了多少」，财务关心「发行与兑付总量」，两者都不需要批次级溯源；细分到 lot 会让分录数量爆炸且对账复杂度翻倍。批次的分摊结果由 `asset_lot` 自身状态承载，一致性由不变量 9 校验。

**过期批处理**（每日 04:00，PM2 instance 0 + Redis 锁 `expire:daily`）：

1. 扫 `expires_at < now() AND remaining > 0` 的批次
2. 每个账户每资产生成一张 `kind='burn'` 凭证，`bizId = sys:expire:{day}:{accountId}:{assetCode}`（天然幂等，重跑安全）
3. 同事务内：`asset_lot.remaining = 0`、`asset_balance.available -= 剩余`、写分录
4. 分批提交（每批 500 账户），避免长事务阻塞
5. 过期量计入 `asset_daily_stat.burned`，`reason = 'expire'`

> `LEDGER_REASONS` 需新增 `expire`。过期属于「凭空消失」，是 `burn` 单边凭证，不要求平衡 —— 这正是 §2.2 里「守恒在积分场景不成立」的具体例证。

### 5.3 并发控制（沿用现有写法，不要退化）

```sql
UPDATE asset_balance
   SET available = available + $3, frozen = frozen + $4, updated_at = now()
 WHERE account_id = $1 AND asset_code = $2
   AND available + $3 >= 0 AND frozen + $4 >= 0
RETURNING available, frozen;
```

- 影响 0 行 = 余额不足，无需 `SELECT FOR UPDATE`

- 唯一冲突（`23505` on `uq_asset_txn_biz_id`）→ 事务回滚 → 回放原凭证，返回 `duplicated: true`

## 6. 关键流程的分录

### 6.1 玩法产出（`issue`，单边）

`bizId = u42:pet:interact:{clientUuid}`

| 账户    | 资产        | delta |
| ------- | ----------- | ----- |
| 玩家 42 | `game_coin` | +12   |

### 6.2 扭蛋（`burn` + `issue` 同一凭证）

`bizId = u42:gacha:draw:{clientUuid}`

| 账户    | 资产          | delta |
| ------- | ------------- | ----- |
| 玩家 42 | `game_coin`   | −100  |
| 玩家 42 | `furn_sofa`   | +1    |
| 玩家 42 | `item_potion` | +3    |

不要求平衡（发行与销毁）。原子性由单事务保证 —— 这就是 G2 的修复。

### 6.3 挂单（`freeze`）

`bizId = u42:market:list:{listingId}`

| 账户    | 资产         | delta | frozen_delta |
| ------- | ------------ | ----- | ------------ |
| 玩家 42 | `skin_tiger` | —     | —            |

实例转移：`item_instance_entry` 玩家 42 `−1` / `ESCROW` `+1`，`item_instance.state = 'escrowed'`。

可堆叠标的则走冻结：玩家 42 `delta −3` / `frozen_delta +3`（总量不变，可用转冻结）。

### 6.4 寄售成交（`transfer`，必须平衡）

`bizId = mkt:{listingId}:settle`，手续费 5%

| 账户  | 资产        | delta | frozen_delta |
| ----- | ----------- | ----- | ------------ |
| 买家  | `game_coin` | −1000 | 0            |
| 卖家  | `game_coin` | +950  | 0            |
| `FEE` | `game_coin` | +50   | 0            |

`SUM(delta) = 0` ✅

实例转移：`ESCROW` `−1` / 买家 `+1`，`state = 'held'`，`tradable_after = now() + cooldown`

### 6.5 竞价（`freeze` → `transfer`）

出价：买家 `delta −1000` / `frozen_delta +1000`
被超越：买家 `delta +1000` / `frozen_delta −1000`
中标结算：买家 `frozen_delta −1000`，卖家 `delta +950`，`FEE` `delta +50` → `SUM(delta) = 0` ✅

```sql
-- 不变量 1：转移凭证内部平衡（能定位到具体凭证）
SELECT e.txn_id, e.asset_code, SUM(e.delta) AS imbalance
  FROM asset_entry e JOIN asset_txn t ON t.id = e.txn_id
 WHERE t.kind = 'transfer' AND t.created_at >= $since
 GROUP BY 1, 2 HAVING SUM(e.delta) <> 0;

-- 不变量 2/3：余额快照 vs 分录累加
SELECT b.account_id, b.asset_code,
       b.available + b.frozen AS snapshot,
       COALESCE(SUM(e.delta), 0) AS derived
  FROM asset_balance b
  LEFT JOIN asset_entry e USING (account_id, asset_code)
 GROUP BY b.account_id, b.asset_code, b.available, b.frozen
HAVING b.available + b.frozen <> COALESCE(SUM(e.delta), 0);

-- 不变量 5/6：实例守恒与 owner 漂移
SELECT instance_id, SUM(delta) FROM item_instance_entry
 GROUP BY 1 HAVING SUM(delta) <> 1;

-- 不变量 8：合规配置未被手工绕过
SELECT code FROM asset_def
 WHERE (tradable AND redeemable) OR (tradable AND gacha_output);

-- 不变量 9：批次聚合 == 余额快照
SELECT b.account_id, b.asset_code, b.available, b.frozen,
       COALESCE(SUM(l.remaining), 0) AS lot_available,
       COALESCE(SUM(l.frozen), 0)    AS lot_frozen
  FROM asset_balance b
  LEFT JOIN asset_lot l USING (account_id, asset_code)
 GROUP BY b.account_id, b.asset_code, b.available, b.frozen
HAVING b.available <> COALESCE(SUM(l.remaining), 0)
    OR b.frozen    <> COALESCE(SUM(l.frozen), 0);

-- 不变量 10：过期作业无遗漏
SELECT id, account_id, asset_code, remaining, expires_at
  FROM asset_lot
 WHERE expires_at < now() AND remaining > 0;

-- 不变量 11：限量未超发（CHECK 已兜底，此处防有人手工改）
SELECT code, minted_count, mint_limit FROM asset_def
 WHERE mint_limit IS NOT NULL AND minted_count > mint_limit;
```

## 8. 风控清单（3b 起为必需项，不是可选）

| R9  | 手续费作为通胀 sink（成交税进 `FEE` 账户即退出流通） | 成交分录                                |
| R10 | 全局交易开关（出事能一键关停市场）                   | `GameConfigService`                     |

另：`AdminAuditInterceptor` 已覆盖后台写操作；后台 `wallet:write` 权限攻破即等于攻破经济系统，交易上线前应先补全项目缺失的限流（见 `安全与运维加固清单.md` A 项）。

### 8.6 回档能力

游戏与金融在此分歧：金融只冲正不回档，游戏出重大事故（数值配错、外挂刷币）需要回档。前提是**分录永不物理删除** + 定期余额快照。归档只允许 `DETACH PARTITION` 后转储，不允许 `DELETE`。

## 10. 明确不做（及放开的条件）

| 不做                                     | 放开条件                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------ |
| 会计科目表、借贷方向、会计凭证、期末结转 | 需要出具财务报表或接受审计                                                     |

| Seata / TCC / Saga 分布式事务            | 账本拆库或拆服务                                                               |
| Redis 缓存余额                           | 永不 —— 缓存余额是对账噩梦的头号来源                                           |

| 玩家提现 / 虚拟资产兑法币                | 永不（§3）                                                                     |
| 法币充值买币                             | 需接微信小游戏虚拟支付，另建订单-回调-发货三段账（属第三类系统，不并入本账本） |

## 附录 A · 与天工项目（tiangonghouduan）的差异

同为「余额快照 + 流水」大类，本设计刻意在四处不同：

| 维度     | 天工                                                              | 本设计                                                                               | 理由                                                                     |
| -------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------ |
| 并发控制 | `SELECT FOR UPDATE` 悲观行锁                                      | 条件原子 UPDATE                                                                      | 免排队、免死锁，且可被已持 Redis 锁的调用方安全复用                      |
| 双录     | 货币「半双录」：写 counterpart 分录但 `balance_before/after` 填 0 | 按凭证类型区分：`transfer` 真双录且系统账户持真实余额，`issue`/`burn` 不假装有对手方 | 半双录付了复杂度成本却只能靠全局 `SUM=0` 启发式校验，无法定位问题凭证    |
| 幂等     | 三层分散（API 表 + 流水唯一键 + 业务单据唯一键）                  | 收敛到 `asset_txn.biz_id` 一处 + Redis 请求级去重                                    | 新增业务不会漏配幂等                                                     |
| 余额修复 | 提供 `recalculate_balance.js` 一键重算                            | 不提供，只能冲正                                                                     | 该脚本忽略 `frozen` 与分桶，会把带冻结账户改错 —— 修复工具本身成为故障源 |

另：天工仓库将 `.env` 与两个 `.env.bak.*` 提交进 git，其中含数据库密码、`JWT_SECRET`、`ENCRYPTION_KEY`、Sealos AK/SK、微信 AppSecret、短信与 OCR 密钥。**这些密钥已泄露，需全部轮换**（删文件无效，历史提交仍可读）。本仓库 `.gitignore` 已正确排除，保持现状。

### 12.3 实现选择（本文未指定的部分）

- **`EconomyService` 保留为货币门面**，而非删除。它不含记账逻辑，只做「池 ↔ 资产 code」与「余额 map ↔ `WalletView`」两次翻译。理由是十余个存量接口的出参形状是 `{ gameCoin, marketingPoint }`，客户端按它渲染；收口一次比让每个玩法自己拼 `balances()['game_coin'].available` 更不容易出错。需要一次动多种资产的场景（扭蛋/购买/兑换）已全部改走 `RewardService.exchange`。
- **`ItemsService.grant` / `grantUnlocked` 合并为一个方法**。两者存在的唯一理由是 Redis 锁不可重入，而记账路径已不再抢锁。这个区分曾让「兑换即时到账」静默降级成人工发货（持锁者调 `grant` 抢不到自己的锁、抛 409、被 catch 吞掉）。
- **`D11` 已定**：`marketing_point` 取 `expire_days = 365`，按自然月末截断归并（每玩家每月至多一行）。
- **重复收藏品的折算改为补偿道具**（原 `dupeCoin` → `dupeItemKey` + `dupeQty`）。D1 之后扭蛋不能产币；同时折算口径收窄为「重复**且不可交易**」——唯一物品实例化之后，可交易皮肤的第二份是能挂到市场卖掉的资产，再塞一份就是正当产出。
- **扭蛋奖池权重重新分配**：移除两档零钱（原占 68% 权重）后并入消耗品档。期望回收约 205 币/抽，仍显著低于 300 的单抽成本，sink 定位不变。
- **`market.enabled` 与四个分档开关默认全 `false`**。代码就位不等于可以开门做生意 —— 手续费率、风控阈值、限价区间都要运营先定。全关状态下市场写接口一律 403。
- **`buyNow` 不接受客户端 `bizKey`**：幂等键固定为 `mkt:{listingId}:settle`。一张挂单只能成交一次，用客户端 bizId 的话两个买家并发买同一件东西会拿到两个不同的键，唯一约束就拦不住第二笔。

### 12.4 运维须知

- 交易上线前需在后台把 `market.enabled` 与 `market.features` 逐档打开，并确认 `market.feeBps`（D4）、`market.priceBand`（D5）、`market.risk`（D12）三项取值。
- `asset_entry` 分区由 `PartitionService` 维护（启动时 + 每月 1 日 03:30 补建，始终保持未来 12 个月）。若日志出现 `asset_entry_default 存在 N 行`，说明曾有月份分区缺失，那些行无法随分区被 `DETACH` 归档，需人工搬迁。
- 定时作业时序：04:00 过期 → 04:10 对账 → 04:20 净流出日报。**顺序不能反**：不变量 10 校验「不存在已过期但仍有余量的批次」，若对账先跑会每天误报。
